# 缺陷排查：先找根因，再改代码

## 何时使用

- 用户报告报错、行为异常、测试失败、构建失败或性能退化。
- 结果与预期不一致，且原因不明确。
- 你已经尝试过一两次修复但没有解决。
- 需要判断问题出在主进程、渲染进程、IPC、网络、数据还是环境。

## 何时不要用

- 明确的功能需求：走 plan-and-execute。
- 纯代码质量审查：走 code-review。
- 只是缺少信息：先读文件/日志，不要把它包装成调试。

## 铁律

**没有完成根因调查，不要提出修复。**

症状修复（重试、吞异常、加延迟、改断言）不是修复。它会让问题变得更难发现。

## 第一阶段：收集证据

### 1. 读完整错误

- 读完整错误信息、堆栈、退出码、日志关键行，不要只看第一行。
- 记录文件、行号、错误码、请求 ID、时间点。
- 区分根错误与后续连锁错误；不要修最后一个报错。

### 2. 稳定复现

- 记录触发步骤、输入、环境、账号/权限、数据状态。
- 判断是必现、偶发还是特定环境；偶发就先加观测，不要猜。
- 用最小输入复现；删掉无关步骤，直到剩下最短路径。
- 如果无法复现，先收集证据（日志、请求、状态快照），不要直接改代码。

### 3. 检查最近变化

- git diff / git log：最近改了什么？
- 依赖、配置、环境变量、数据格式是否变化？
- 是否只在某个平台、某个版本、某个用户目录出现？

### 4. 在组件边界加观测

多组件系统（UI → IPC → 服务 → 数据库/外部 API）不要凭感觉猜。先在每个边界记录：

- 进入组件的数据、参数、状态。
- 离开组件的结果、错误、耗时。
- 环境/配置是否按预期传递。

运行一次，找到**第一个**出现异常的地方，再深入那一层。不要同时在五层加日志然后猜。

Electron 项目常见边界：

- 渲染层（React/store）→ preload → 主进程 IPC。
- 主进程服务 → 文件系统/子进程/网络。
- WebContentsView / 自定义协议 / iframe 沙箱。
- 终端 PTY → shell → 命令输出。
- 打包后的 asar 路径、数据目录、权限/令牌。

### 5. 写出当前假设

用一句话写出你认为的原因，以及什么证据能证明/推翻它。例如：

> 假设：预览失败是因为本地服务还没监听端口，而不是浏览器视图 bounds 为 0。证据：如果延迟启动服务后重试成功，且 debugInfo 显示 bounds 正常，则假设成立。

## 第二阶段：缩小范围

- 二分：注释/禁用一半逻辑、按提交二分、按输入缩小。
- 对比：正常与异常路径的输入、状态、依赖版本有什么不同。
- 替换：用已知正常的实现/数据替换可疑部分，看问题是否消失。
- 追踪：从错误点反向追到第一个错误状态，而不是从入口正向猜。
- 一次只改一个变量；同时改三处，即使好了也不知道为什么。

## 第三阶段：修复

- 改最小必要范围，保持现有接口和行为。
- 先写一个能复现缺陷的测试（如果项目有测试框架），确认它失败。
- 修复后运行同一个测试，确认通过；再跑相关回归。
- 检查同类调用点是否也有同样问题；不要只修用户看到的那一处。
- 如果修复需要改变行为/接口/数据格式，说明影响和迁移方案。

## 第四阶段：验证与交付

- 证明修复前失败、修复后通过；不要只跑一次通过就结束。
- 运行相关单元/集成/E2E/构建；UI 问题在真实页面检查。
- 确认没有引入新的日志噪音、性能问题或权限扩大。
- 交付说明：根因、修复点、验证证据、残余风险、相关文件路径。

## 常见根因类型

- **空值/缺省**：上游没校验，下游崩溃；真正原因在上游。
- **竞态**：异步顺序、重复点击、取消后仍回调。
- **边界**：空数组、超长文本、特殊字符、时区、编码。
- **状态不同步**：缓存、store、数据库、UI 各有一份状态。
- **路径/权限**：工作区外路径、符号链接、大小写、Windows 保留名。
- **环境差异**：开发能跑、打包失败；PATH、shell、临时目录、权限令牌。
- **资源泄漏**：监听器/定时器/进程/句柄未清理，累积后崩溃。
- **外部依赖**：API 变更、超时、限流、返回格式变化。
- **假设错误**：代码按错误的前提编写，测试也只覆盖了这个前提。

## 调试记录模板

~~~markdown
## 现象
- 用户看到：
- 复现步骤：
- 环境：
- 完整错误/日志：

## 已确认事实
- ...

## 假设与验证
1. 假设：...；验证：...；结果：成立/推翻
2. ...

## 根因
- 第一处错误状态：
- 为什么会发生：
- 为什么之前没发现：

## 修复
- 改动：
- 回归测试：
- 验证命令与结果：

## 残余风险
- ...
~~~

## 常见反模式

- **猜着改**：改一处跑一下，没有假设，最后不知道哪处起了作用。
- **重试/吞异常**：把错误藏起来，用户下次遇到更难查。
- **改断言/跳过测试**：让测试变绿，而不是让行为正确。
- **只修表象**：空指针加个判空，但不解决上游为什么传空。
- **同时改多处**：无法归因，也无法回退。
- **忽略环境**：开发环境正常就认为打包版正常。
- **不写回归测试**：同样的问题下次还会回来。
- **过度重构**：借修 bug 之机重写整个模块，引入新风险。

## 停止条件

遇到以下情况，停下来向用户说明，而不是继续试：

- 需要生产数据/真实账号才能复现，而当前没有授权。
- 修复会改变用户数据、公共 API 或不可逆状态。
- 问题来自外部服务/平台，当前无法控制。
- 已经尝试多个假设仍无证据，需要用户提供日志/环境信息。
- 继续调试的成本明显高于影响，需要用户决定优先级。

## 与其他技能的配合

- 修复前审查风险：code-review。
- 补回归测试：test-writer。
- 交付前验证：verify-before-delivery。
- 安全相关缺陷：security-audit。
