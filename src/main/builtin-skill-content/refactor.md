# 安全重构：行为不变，小步可验证

## 何时使用

- 用户要求整理代码、拆分模块、消除重复、改名或改善可读性，但不改变功能。
- 需要为后续功能腾出结构，但当前行为必须保持。
- 代码难以测试/维护，需要在不动外部行为的前提下改善内聚与边界。

## 何时不要用

- 修复缺陷：先 debugging；借重构夹带修复会让 diff 难以审查。
- 需求变更：走 plan-and-execute，明确行为会变。
- 没有基线测试且无法验证行为：先补 characterization test，或缩小到可验证的改动。
- 时间紧迫、风险高、收益不明确：重构不是优先级。

## 定义「行为不变」

重构的完成标准是：外部可观察行为一致，代码更易理解/维护。

必须保持的通常包括：

- 公共 API、导出、函数签名、返回值与错误类型。
- 文件格式、序列化、配置字段、默认值。
- CLI 参数、环境变量、日志中用户依赖的关键字段。
- 性能量级和资源使用（不能从 O(n) 变成 O(n²)）。
- UI 文案、交互流程、可访问性。

如果必须改变其中任何一项，这不是纯重构，要明确告知用户并给出迁移方案。

## 流程

### 1. 明确边界

写下：

- 哪些行为必须保持不变。
- 允许改哪些文件/模块。
- 不允许改哪些公共接口。
- 如何验证行为未变。

### 2. 建立基线

- 运行现有 typecheck/测试/构建，记录通过状态。
- 缺少关键测试时，先补最小的行为测试（characterization test），固定当前正确行为。
- 保存关键输入/输出样例，供重构后对比。

### 3. 小步修改

一次只动一个关注点：

- 提取函数/模块。
- 移动文件并更新引用。
- 改名并保持导出兼容。
- 消除重复，但不要过度抽象。
- 引入依赖注入/纯函数边界，便于测试。

每步之后运行相关验证；不要积累十步再一起跑。

### 4. 保持兼容

- 谨慎改变导出、默认值、路径和序列化格式。
- 必须变更公共 API 时：提供兼容层、迁移说明或版本化。
- 旧数据/旧配置要能读取；不能静默丢弃。
- 删除代码前确认没有调用方（grep/类型检查/测试）。

### 5. 不夹带

- 不顺手改无关格式、不升级依赖、不修无关 bug。
- 发现的问题单独记录，交给用户决定。
- 不为了「更优雅」引入新的框架或抽象层。

### 6. 最终验证

- 全量相关测试、typecheck、build。
- 对比重构前后的关键行为/输出。
- 查看 diff：是否只包含预期改动，是否有意外删除。
- 说明结构变化前后对比、验证命令、残余风险。

## 重构手法

- **提取函数**：把一段有明确输入输出的逻辑变成纯函数。
- **提取模块**：按职责拆分，不按文件类型机械拆分。
- **内联**：过度抽象的薄包装直接去掉，减少间接层。
- **改名**：让名字表达意图；保持导出别名直到调用方迁移。
- **参数对象**：参数过多时聚合，但不要制造万能对象。
- **依赖注入**：把外部依赖（时间、IO、网络）从核心逻辑中分离。
- **消除重复**：只合并真正相同的逻辑；相似但会独立演化的代码不要强行合并。
- **移动边界**：把业务规则从 UI/框架代码中移到可测试的领域层。

## 判断标准

- 代码是否更容易理解？如果一个新人读不懂，重构没有达到目的。
- 是否减少了真实的重复/耦合，而不是增加抽象层？
- 行为是否可验证地保持不变？
- diff 是否足够小，能在一次审查中看懂？
- 是否为后续需求创造了清晰的扩展点，而不是猜测未来？

## 常见反模式

- **大爆炸重构**：一次改几十个文件，无法审查、无法归因。
- **借机改需求**：在重构中顺手改行为，测试和用户都被误导。
- **过度抽象**：为两个相似函数造一套框架，增加理解成本。
- **删除旧代码不留兼容**：调用方/旧数据直接崩。
- **没有基线**：改完只能靠感觉判断行为是否一致。
- **只跑一个新测试**：相关回归没跑，隐藏破坏。
- **追求行数更少**：可读性和边界清晰比行数重要。

## 与其他技能的配合

- 行为验证：test-writer、verify-before-delivery。
- 风险审查：code-review。
- 重构中发现缺陷：debugging。
- 大范围机械改动：parallel-work，但要确保文件所有权不冲突。
