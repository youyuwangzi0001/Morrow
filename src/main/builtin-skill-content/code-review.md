# 代码审查：只读地找出真实风险

## 何时使用

- 用户要求 review、审查代码、合并前检查、看某次改动有没有问题。
- 你刚完成一处改动，准备提交或交付前做自检。
- 需要判断一个补丁是否可以安全合并。
- 需要向作者解释问题的影响、触发条件和修复方向。

## 何时不要用

- 用户要求直接修复：先按 debugging 找根因，修复后再按本技能自检；不要只做口头审查。
- 安全专项审计、渗透测试：进入 security-audit。
- 纯风格/格式问题且项目没有明确规范：不要用个人偏好占据审查结论。

## 原则

**审查的是行为与风险，不是作者。** 只读，不修改文件；需要验证时先说明并征得同意。

**先理解意图，再看实现。** 不知道代码应该做什么，就无法判断它是否做对。先读需求、提交信息、测试、调用方和相邻代码。

**按严重程度排序。** 先报告会导致数据损坏、安全问题、线上故障的问题，再报告可维护性和风格问题。

## 流程

### 1. 确定范围

- 优先看 diff：git diff、git diff --stat、最近提交；没有 diff 时通读改动文件及调用方。
- 记录改动目的：修什么缺陷、加什么能力、影响哪些用户路径。
- 标出未覆盖的范围：没有改但受影响的模块、旧数据、配置、迁移。

### 2. 读调用链

- 谁调用这段代码？输入从哪里来？输出去哪里？
- 失败时调用方期待什么？返回 null、抛错、重试还是降级？
- 有没有共享状态、缓存、并发、事务或生命周期问题？
- 旧数据/旧配置在升级后还能工作吗？

### 3. 按清单检查

#### 正确性

- 边界值：空、0、负数、极大值、超长字符串、Unicode、时区、闰年。
- 空值与缺省：undefined/null/空数组/空对象是否会导致崩溃或错误行为。
- 错误分支：异常是否被捕获、是否正确传播、是否吞掉关键错误。
- 状态更新：条件分支是否都能到达正确状态；有没有遗漏的 return。
- 类型与单位：数字/字符串、毫秒/秒、字节/KB、百分比 0–1 还是 0–100。
- 幂等与重复操作：重复点击、重复提交、重试会不会产生副作用。

#### 安全

- 命令/SQL/模板/HTML 注入：外部输入是否被拼接进执行上下文。
- 路径穿越：绝对路径、..、符号链接、盘符、UNC、zip-slip；是否 realpath 后校验边界。
- 权限：只读/聊天模式是否硬拦截；审批能否被绕过；默认拒绝是否生效。
- 密钥与隐私：凭据是否落盘明文、进日志、进错误信息或提示词。
- 外部内容：网页/MCP/文件内容是否被当作指令或授权。
- XSS/CSRF/SSRF：渲染、跳转、代理、下载是否有边界。

#### 并发与资源

- 竞态：共享状态、异步顺序、取消与超时。
- 重复提交/重入：锁、队列、幂等键是否有效。
- 资源泄漏：定时器、监听器、进程、文件句柄、WebContents、PTY 是否清理。
- 背压：无界队列、无限重试、内存增长。

#### 兼容与回归

- 公共 API、导出、序列化格式、默认值是否变化。
- 调用方是否同步修改；旧客户端/旧数据是否仍可用。
- 数据库/配置文件迁移是否可逆、是否有回退。
- 平台差异：Windows 路径、编码、大小写、权限。

#### 性能

- 是否有明显的 O(n²)、重复 IO、无界缓存、频繁重渲染。
- 大文件/大列表是否有分页、截断或流式处理。
- 性能结论是否有测量或复杂度依据，而不是猜测。

#### 测试

- 关键分支是否有测试；失败路径和边界是否覆盖。
- 测试是否断言可观察行为，而不是实现细节。
- 是否存在为了通过而放宽断言、跳过用例或依赖固定 sleep。

#### UI（如涉及）

- 默认、悬停、焦点、按下、禁用、加载、空、错误、长文本、窄屏。
- 键盘可达、aria 标签、对比度、减少动效。
- 状态变化后是否有可见反馈；错误是否可恢复。

### 4. 给出证据

每个问题都要能定位：

- 文件与行号（或函数名）。
- 触发条件：什么输入/状态/操作会出问题。
- 影响：用户看到什么、数据会怎样、是否安全。
- 建议：最小修复方向，不要求你直接改。
- 置信度：确定 / 很可能 / 需要验证。

不要写「这里可能有问题」这种无法行动的评论。

### 5. 输出

~~~markdown
## 结论
可以合并 / 需要修改后合并 / 不建议合并

## 必须修（严重）
1. 文件:行 - 问题 - 触发条件 - 影响 - 建议

## 建议修（中等）
...

## 可选（轻微）
...

## 已检查范围
- 模块/文件/场景
- 运行的测试或未运行的原因

## 残余风险
- 未覆盖的路径、依赖外部系统的行为、需要人工验证的 UI
~~~

## 自检清单

- 我是否理解了这段代码的意图，而不是只按风格挑刺？
- 是否检查了失败路径和边界，而不只是 happy path？
- 是否把安全问题与普通 bug 分开排序？
- 每个问题是否都有具体位置和触发条件？
- 是否说明了没有覆盖的范围？
- 是否避免了无关的重构建议？

## 常见反模式

- **风格警察**：把个人偏好当阻塞问题，忽略真正的正确性风险。
- **只看 diff**：不看调用方和旧数据，漏掉回归。
- **猜测式评论**：没有复现或证据就说「可能有竞态」。
- **过度要求**：要求作者顺手重构无关代码、升级依赖或改变公共 API。
- **只报问题不给方向**：作者不知道下一步怎么修。
- **越权修改**：审查过程中直接改代码，混淆审查与实现。
- **忽略测试**：只看实现，不检查测试是否真的覆盖行为。

## 与其他技能的配合

- 需要修复：debugging。
- 安全深挖：security-audit。
- 验证修复：verify-before-delivery。
- 大范围并行审查：parallel-work。
