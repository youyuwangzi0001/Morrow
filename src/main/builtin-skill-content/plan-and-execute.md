# 计划与执行：从可验证的步骤到真实完成

## 何时使用

- 任务需要多个步骤、多个文件或多种工具，不能一次完成。
- 用户在计划模式（plan mode）里要求先看方案再执行。
- 用户建立了目标（Goal），需要跨多轮持续推进。
- 任务超过一次回答的容量，或需要先探索再决定实现方式。
- 用户说「先规划一下」「分步骤做」「不要一口气写完」。

简单的一句话问答、单文件小修、明确的命令执行，不需要套完整计划。

## 三种工作方式

| 方式 | 适合 | 关键工具 | 完成标准 |
|---|---|---|---|
| 计划模式 | 改动大、方向需要用户确认、只读探索后提交方案 | submit_plan、todo_write | 用户批准计划，再开始写入 |
| 目标模式 | 用户明确要求跨多轮无人值守推进 | update_goal、todo_write | 完成证据通过校验，或诚实标记 blocked |
| 普通执行 | 步骤清楚、规模中等 | todo_write | 每一步验证通过并更新状态 |

不要把普通任务擅自升级成目标；只有用户明确要求目标模式时才使用 update_goal。

## 计划模式：先只读，再提交

计划模式是只读阶段。批准前不要写文件、不要执行有副作用的命令。

### 1. 勘察

- 读需求、相关代码、调用方、测试、配置和数据。
- 用 list_dir / glob / grep 建立文件地图；不要凭文件名猜实现。
- 找出真正的改动点、依赖关系、风险和未知项。
- 记录你已经确认的事实，以及还需要验证的假设。

### 2. 拆步骤

计划里的每一步都要满足：

- **可执行**：说清改哪个文件/目录、用什么方法，不写「优化一下」。
- **可验证**：每步都有检查方式（命令、测试、页面操作、文件内容）。
- **有顺序**：标出依赖关系；能并行的步骤明确说明。
- **有边界**：哪些文件不能动，哪些行为必须保持。
- **可回退**：高风险步骤要有回退或备份方案。

计划模板：

~~~markdown
## 目标
用一句话说清完成后什么会变成真的。

## 现状与关键发现
- 入口在 src/...；当前行为是...
- 约束：不能改公共 API；现有测试覆盖...

## 步骤
1. [ ] 在 A 文件补 X，验证：运行 Y 测试
2. [ ] 在 B 文件接入 Z，验证：手动打开页面检查...
3. [ ] 补回归测试，验证：新增用例先失败后通过

## 风险与回退
- 风险：...；回退：保留旧分支/备份文件...
- 未确认：...；执行前先查...

## 验收
- 命令：typecheck / test / build
- 行为：...
- 不包含：...
~~~

### 3. 提交并等待

用 submit_plan 提交计划，然后停下等待用户批准、修改或拒绝。不要一边等一边偷偷执行。

用户要求修改时，先理解修改点，更新计划后重新提交；不要只改一句口头说明。

### 4. 执行

批准后按步骤执行：

- 开始一步前，把 todo 标为 in_progress；完成并验证后再标 completed。
- 一次只推进一个可验证的步骤，不要同时改十个文件。
- 每步完成后运行对应检查；失败就停在当前步修，不要带着坏状态往下走。
- 发现计划与现实不符时，说明偏差并调整计划；改变范围前先征得同意。
- 阶段性向用户汇报：完成了什么、验证结果、下一步。

## 目标模式：写完成契约，不写努力描述

目标不是任务描述，而是完成契约。它必须说明：什么必须变成真的、怎么证明、允许改哪里、卡住时怎么办。

### 完成契约的五个部分

1. **终态**：具体、可观察的结果。测试全绿、队列清空、报告文件存在、页面可交互。
2. **证据**：能运行的检查或能检查的文件。命令退出码、测试数量、grep 零命中、产物路径。
3. **边界**：只能改哪些目录/模块，不能做哪些破坏性操作。
4. **循环**：如何迭代。每次修改后重跑检查；按队列逐项处理。
5. **停止规则**：什么情况下停止并报告，而不是硬撑或假装完成。

强弱对比：

- 弱：把项目优化好。强：修复 test/auth 下所有失败用例，npm test 退出码为 0，不改 test/ 与 src/auth 之外的文件；无法修复的用例记录位置与原因。
- 弱：让页面更快。强：把首屏 LCP 降到 2.5 秒以内，用 lighthouse 报告验证；连续三次尝试达不到就报告最好结果与瓶颈。
- 弱：继续完善报告。强：报告包含方法、发现、限制三节，所有数字能追溯到 data/ 下的源文件，导出 PDF 后页数与目录完整。

### 每轮必须更新目标

只要目标处于 active，每轮结束前调用 update_goal：

- 有推进但未完成：status=active，写 summary 与 nextStep。
- 全部完成且验证通过：status=completed，evidence 必须是本目标期间在工作区内真实生成或更新的非空文件路径。
- 无法继续：status=blocked，写清阻塞原因和用户需要做什么。

不要用「差不多完成」或「应该可以」代替证据；不要为了结束而标记 completed。

## 长任务与上下文

- 把关键决定、文件清单、验证命令写进 todo 或工作区笔记，不要只留在对话里。
- 长计划可以分阶段：每阶段有独立验收，阶段完成后再进入下一阶段。
- 上下文被压缩后，先读自己的笔记和当前文件状态，再继续；不要凭记忆重复已完成的工作。
- 任务全部完成后如果还在打磨，追加「收尾完善」步骤，不要提前宣布全部完成。

## 执行中的沟通

- 开始前：一句话说明计划和第一步。
- 步骤完成：简短说明结果与验证，不要粘贴整段日志。
- 遇到阻塞：说明卡在哪、已尝试什么、需要用户做什么决定。
- 计划变化：说明为什么变、影响哪些步骤、是否需要重新确认。
- 完成时：给出结果位置、验证证据、未覆盖的风险。

## 计划质量检查

- 每一步是否都能在完成后明确判断「通过/不通过」？
- 是否标出了不能动的文件和必须保持的行为？
- 是否先处理高风险/高不确定性的部分，而不是把难点留到最后？
- 是否有最小可交付路径？即使时间不够，也能交出可用的一部分。
- 是否避免了为简单任务写过度复杂的计划？

## 常见反模式

- **计划表演**：写了很多听起来专业的步骤，但没有文件、命令和验收。
- **先做后补计划**：已经改完才提交计划，用户无法真正选择方向。
- **状态虚报**：没运行测试就把 todo 全标 completed；目标没有证据就标完成。
- **范围漂移**：执行中顺手加功能、改无关文件，最后交付物和计划不一致。
- **无限打磨**：主路径已完成却一直改细节，不告诉用户可以先验收。
- **遇到失败就换方案**：不定位原因，直接绕开，留下隐藏问题。
- **把目标写成努力**：「持续优化」「尽量完善」没有终点，无法判断何时停止。

## 与其他技能的配合

- 需求不清：先 brainstorm-and-scope。
- 需要运行验证：verify-before-delivery。
- 多模块并行：parallel-work。
- 缺陷排查：debugging；安全风险：security-audit。
