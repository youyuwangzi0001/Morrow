# 先想清楚，再动手：需求澄清与方案收敛

## 何时使用

- 用户的目标还很模糊：「做个好看的网站」「优化一下体验」「帮我分析这份数据」，但没说清给谁、用来做什么、什么算完成。
- 新功能、新产品、新视觉作品，方向选择会显著影响后面几十步的工作。
- 用户提出「都行」「你看着办」「先做个版本看看」，但不同理解会带来完全不同的成品。
- 需要在两三个方案之间做取舍，而不是直接进入实现。

## 何时不要用

- 明确的缺陷修复、单文件小改动、已有计划的执行步骤：直接进入 debugging 或 plan-and-execute。
- 用户已经把目标、验收和限制说清楚：不要为了走流程再问一遍。
- 纯粹的代码审查：进入 code-review。
- 用户明确说「先按你的判断做一版」：给出一版可工作的假设，写清假设，直接做，不要反复盘问。

## 核心原则

**先定义问题，再定义方案；先定义验收，再开始构建。**

一个可执行的任务说明，至少要回答：

1. 给谁用：具体的人、角色或场景，不是「所有用户」。
2. 解决什么：用户现在的困难是什么，完成后能多做什么。
3. 交付什么：网页、应用、报告、表格、图片、文档，还是代码改动。
4. 什么算完成：可观察的结果、必须覆盖的内容、不能出现的问题。
5. 边界是什么：不做什么、不能动什么、时间/环境/依赖限制。

没有这五项时，不要直接写第一行代码。

## 工作流程

### 1. 复述问题

先用一句话复述你理解的目标，并列出你识别到的约束：

> 你要的是给第一次使用的客户看的产品介绍页，重点是把三个套餐讲清楚，而不是做一整套官网；需要中文、手机可看、能直接发给客户。

如果复述错了，用户会立刻纠正，比做到一半再返工便宜得多。

### 2. 只问真正影响方向的问题

优先从工作区、对话历史、已有成品和项目说明里找答案。不要问用户已经说过、或你能通过读文件确认的事。

需要用户拍板时，一次只问一个关键决策，优先用 ask_user 给出 2–3 个有区别的选项；不要把所有细节列成问卷。可以自行决定的小事（文件名、按钮文案、间距）先做合理假设，并在简报里写明。

常见的关键决策：

- 这是「快速验证想法」还是「要直接交付给客户」？两者对完成度要求不同。
- 更看重速度、完整度还是视觉表现？资源有限时必须排序。
- 有没有现成品牌、模板、数据或技术栈必须沿用？
- 成品要给谁看、在什么设备/软件里打开？

### 3. 发散的三个方向

不要只给一个方案再加两个换色版本。给出 2–3 个**结构上不同**的方向，每个方向写清：

- 核心主张：一句话说清它为什么成立。
- 用户第一眼看到什么。
- 代价：需要多少工作量、依赖什么、风险在哪。
- 适合什么情况。

例如做产品介绍页：

1. **单页叙事**：首屏主张 + 三段价值 + 价格 + 行动按钮，适合直接投放。
2. **可交互演示**：首屏就能操作核心功能，适合让客户快速理解产品。
3. **案例驱动**：用三个真实场景串起功能，适合建立信任。

如果三个方向都指向同一种实现，说明你还没有真正发散。

### 4. 收敛并写简报

按「目标匹配度、用户价值、实现风险、可验证性」四个维度选一个方向。把选择理由写出来，不要只给结论。

简报模板：

~~~markdown
# 任务简报

## 一句话目标
给「第一次了解产品的客户」一份手机可看的产品介绍页，重点讲清三个套餐的差异。

## 用户与场景
- 用户：准备采购的中小团队负责人
- 场景：销售在微信里直接发链接，对方在手机上打开
- 成功标准：30 秒内能说清「适合谁、多少钱、下一步做什么」

## 交付物
- 单文件 HTML，中文，手机优先，可直接在浏览器打开
- 含首屏、价值点、套餐对比、常见问题、行动按钮

## 必须做到
- 三个套餐的价格、额度、适用人数准确
- 首屏在 390px 宽下不横向滚动
- 所有按钮有明确结果，不留占位链接
- 打印/PDF 时不截断关键内容

## 明确不做
- 不做登录、支付、后台
- 不接真实表单，先用 mailto 或复制联系方式
- 不做多语言

## 关键假设
- 「三个套餐」沿用用户提供的名称与价格；如果没有，先用占位名并标注待确认
- 视觉方向采用克制的工业感，与客户现有的深色品牌一致

## 验收方式
- 在 390px / 768px / 1440px 三种宽度下打开检查
- 点击所有按钮，确认有可见反馈
- 用浏览器打印预览检查分页
~~~

### 5. 交给下一步

- 涉及视觉新作：把简报交给 frontend-art-direction，继续写视觉方向与构图。
- 涉及多步骤实现：把简报交给 plan-and-execute，拆成可验证步骤。
- 涉及数据/报告：把口径与验收写进 data-analysis 或 document-deliverables。
- 涉及外部事实：先进入 web-research 查证，不要在简报里编数据。

## 质量检查

- 一个没参与对话的人读完简报，能否知道要做什么、不做什么、怎么验收？
- 每个「必须做到」是否可观察、可测试？「体验好」不是验收标准，「390px 下无横向滚动」才是。
- 是否写了明确的不做清单？没有边界的任务一定会膨胀。
- 是否把假设和事实分开？假设要标注，事实要有来源。
- 是否避免了「现代简约」「高级感」这类无法执行的形容词？把它们翻译成颜色、字体、布局、交互的具体选择。

## 常见反模式

- **审问式澄清**：连续问十几个问题，用户还没看到任何东西就累了。先做能做的调研，只问决定方向的问题。
- **伪选项**：三个方案其实是同一个布局换三种颜色。方案必须在结构或策略上不同。
- **过早实现**：还没确认用户是谁、成功标准是什么，就开始写代码；后面大概率整体推翻。
- **把假设藏起来**：默默替用户决定价格、品牌、功能范围，交付时才暴露。
- **没有非目标**：什么都想加，最后每个部分都做不深。
- **用流程拖延**：小改动也要求用户填完整简报。任务越小，简报越短，一句话也可以。

## 交付

给用户的回复保持短：一句话复述目标，列出你选择的方案和关键假设，再说明下一步会做什么。不要把整份简报原样贴给用户，除非用户要求看。
