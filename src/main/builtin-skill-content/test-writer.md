# 编写测试：先证明能抓住问题，再让实现通过

## 何时使用

- 用户要求补测试、加回归保护、提高覆盖率。
- 新增功能或修复缺陷，需要可重复的验收。
- 重构前需要行为基线。
- 发现测试只覆盖 happy path，失败路径没有保护。

## 何时不要用

- 一次性脚本、临时实验、生成代码：写测试的成本高于收益；先说明。
- 纯视觉主观判断：可以写截图/交互测试，但不要把「好看」写成断言。
- 项目没有任何测试框架且用户不想引入：先做最小手动验证计划，不要强行搭框架。

## 核心原则

**测试行为，不测试实现。** 断言用户/调用方能观察到的结果：返回值、错误、文件内容、事件、页面状态，而不是私有函数被调用了几次。

**先失败，再通过。** 新测试必须能证明它覆盖的问题；如果测试从未失败过，你不知道它是否真的有效。

**测试是资产，不是负担。** 稳定、可读、可定位失败的测试才有价值；为了覆盖率堆无意义断言只会增加维护成本。

## 流程

### 1. 读现有测试

- 找到测试目录、命名规则、运行命令、fixture/helper。
- 沿用同一套框架和风格；不要为了一个用例引入新框架。
- 读相邻测试，了解项目如何构造临时目录、mock 外部服务、启动应用。

### 2. 列行为清单

按风险排序：

- 正常路径：最重要的用户旅程。
- 边界：空、0、负数、极大值、超长、Unicode、时区。
- 错误：无效输入、依赖失败、超时、取消、权限拒绝。
- 并发/重复：重复提交、竞态、重入。
- 兼容：旧数据、旧配置、迁移。
- 回归：这次修复对应的具体缺陷。

不是每个功能都需要全部覆盖；优先保护「坏了会严重后果」和「最容易坏」的部分。

### 3. 选择层级

| 层级 | 适合 | 代价 |
|---|---|---|
| 单元测试 | 纯函数、解析、校验、状态转换 | 快、稳定，但可能脱离真实集成 |
| 集成测试 | IPC、数据库、文件系统、服务协作 | 中等，能抓到接口问题 |
| 端到端 | 关键用户旅程、真实 UI、打包产物 | 慢、易碎，只覆盖核心路径 |

优先在低层级覆盖细节，用少量 E2E 保护关键旅程。不要把所有逻辑都塞进 E2E。

### 4. 写失败测试

- 新功能：先写期望行为的测试，运行并确认失败原因是「功能不存在」。
- 修缺陷：先写复现缺陷的测试，运行并确认失败原因与用户报告一致。
- 重构：先补 characterization test，固定当前正确行为，再改结构。
- 不要为了让测试通过而提前改实现；先看它按预期失败。

### 5. 实现并验证

- 写最小实现让测试通过；不要顺手加未测试的功能。
- 运行单个测试 → 相关测试文件 → 全量相关套件。
- 失败时读完整输出，确认是断言失败还是环境/编译错误。
- 修复后重跑；如果测试仍然失败，回到调试，不要改断言。

### 6. 清理与交付

- 删除调试输出、临时文件、固定 sleep。
- 确认测试之间互不影响，可以单独运行、重复运行、并行运行。
- 交付说明：新增文件、覆盖场景、运行命令、结果、未覆盖范围。

## 测试设计清单

- 测试名是否描述行为，而不是实现？例如「拒绝空路径」比「test validate 2」好。
- 每个测试是否只验证一个主要行为？
- 是否断言了错误类型/错误信息中稳定的部分？
- 是否覆盖了失败后的状态（没有半写入、没有脏缓存）？
- 是否避免依赖当前时间、随机数、网络和机器路径？必须依赖时是否注入/固定？
- 是否使用真实临时目录并在结束后清理？
- mock 是否只用于外部边界（网络、付费服务、系统 API），并验证了调用参数？
- 测试是否能在 CI/另一台机器上稳定运行？

## 常见测试类型示例

### 边界与错误

- 输入为空、只有空格、超长、包含控制字符。
- 文件不存在、路径是目录、符号链接指向工作区外。
- 权限拒绝、超时、取消、重复调用。
- 依赖返回格式错误、部分成功、限流。

### 状态机

- 合法状态转换全部覆盖。
- 非法转换被拒绝，状态不变。
- 中断/恢复后状态一致。

### UI

- 主路径可操作，按钮有结果。
- 加载、空、错误、禁用状态可见。
- 键盘可完成关键操作，焦点可见。
- 窄屏无横向滚动，深色/浅色都检查。

### 回归

- 用最小输入复现用户报告的缺陷。
- 断言修复后的可观察结果，而不是内部实现。
- 确认修复前测试失败（必要时临时撤回修复验证）。

## 运行与证据

- 使用项目已有命令：typecheck、test:unit、test:e2e、build。
- 记录实际输出：通过数、失败数、耗时、退出码。
- 只跑一个测试时，交付前补跑相关套件，避免漏掉回归。
- 不稳定测试：先找根因（时间、顺序、共享状态、网络），不要用 sleep/重试掩盖。

## 常见反模式

- **为了覆盖率写空断言**：测试通过但什么都没验证。
- **只测 happy path**：错误路径完全没有保护。
- **断言实现细节**：私有函数调用次数、内部变量名，重构就碎。
- **过度 mock**：mock 了被测逻辑本身，测试永远通过。
- **共享状态**：测试之间依赖执行顺序，单独跑就失败。
- **固定 sleep**：慢且不稳定；应等待可观察条件。
- **改断言迁就实现**：实现错了却把期望改对。
- **删除失败用例**：把问题藏起来。
- **E2E 覆盖一切**：慢、脆弱、定位困难；应在低层级覆盖细节。

## 与其他技能的配合

- 缺陷复现：debugging。
- 重构基线：refactor。
- 交付前全量验证：verify-before-delivery。
- UI 视觉检查：frontend-art-direction。
