# 技能编写：把可复用的判断写成按需加载的流程

## 何时使用

- 用户要求创建、修改或优化一个技能（SKILL.md）。
- 同一种判断、流程或验收标准会反复出现，值得沉淀给 Agent。
- 现有技能触发不准、步骤太泛、太长，或经常被模型忽略、执行走样。
- 需要把一次成功的工作方法抽象成可复用流程，而不是复制一份文档。

## 何时不要用

- 一次性任务：不值得沉淀。
- 能用脚本、schema、测试或模板强制执行的规则：优先自动化，不要靠模型自觉。
- 只适用于当前项目的约定：写进项目说明/AGENTS.md，而不是通用技能。
- 纯资料堆砌：技能要提供判断、顺序和验收，不是官方文档的副本。
- 用户只是让你「写长一点」：长度不是质量；先确认要解决的失败模式。

## 先判断值不值得写

值得写：

- 需要判断、取舍、顺序和验收的流程。
- 同一类问题反复出现，新手容易做错。
- 有明确触发场景和可观察的完成标准。
- 能显著减少来回沟通、返工或漏项。

不值得写：

- 一句话能说清的规则。
- 纯文件格式说明，除非包含复杂决策。
- 工具/schema/校验已经强制的约束。
- 只适用于当前这一个任务的路径、变量或临时状态。

## 技能是什么

技能是一份**按需加载的 playbook**，不是常驻系统提示，也不是工具或授权。

它由三部分组成：

1. **元数据**：name + description，始终在上下文里，决定「什么时候想起这个技能」。
2. **正文**：SKILL.md，命中后才读取，告诉 Agent 怎么做、何时停、怎么验收。
3. **资源**：references/assets 等，需要时再读，避免把长资料塞进上下文。

Morrow 的技能安装器只接受 Markdown、文本、JSON/YAML/CSV 和图片，不接受 .js/.py/.sh/.exe 等可执行文件。需要脚本时，在技能正文里描述命令或让 Agent 在工作区生成脚本，不要把可执行文件打进技能。

## 第一原则：省上下文

模型本身已经很聪明。技能只补它**不知道、容易忘或容易走偏**的部分：

- 只写完成任务真正需要的判断、步骤、禁忌和验收。
- 不解释模型已经知道的通用常识。
- 不重复系统提示里的安全、权限、输出规范；需要时引用技能名。
- 例子只保留能改变行为的对比例子，不要写成长篇教程。
- 正文默认控制在 100–250 行；超过 300 行考虑拆分或把长资料放进 references。

写每一段前问自己：**删掉它，模型会做错吗？** 如果不会，就删。

## 给多少自由度

按任务的脆弱程度选择写法：

| 自由度 | 适用 | 写法 |
|---|---|---|
| 高 | 多种做法都成立、依赖上下文判断 | 写原则、判断标准和取舍，不写死步骤 |
| 中 | 有推荐模式，但允许变体 | 写流程框架、参数和检查点，允许按环境调整 |
| 低 | 步骤脆弱、必须一致、容易出错 | 写明确顺序、命令、输入输出和失败处理 |

不要把所有技能都写成低自由度的死脚本；也不要把高风险流程写成「自行判断」。

## 创建一个技能

### 1. 先找失败模式

不要先写结构。先回答：

- 用户会怎么说，才应该触发这个技能？
- 没有这个技能时，模型最常犯的错是什么？
- 有了它，输出应该具体变成什么样？
- 什么情况下**不应该**触发？

至少举一个真实场景。没有失败模式的技能，通常只是资料摘抄。

### 2. 设计最小内容

- **必须写进正文的**：触发后的判断、顺序、边界、验收。
- **可以放 references 的**：长表格、规范、API 文档、品牌资料。
- **可以放 assets 的**：模板、图片、字体等最终产物要用的文件。
- **不该写的**：README、CHANGELOG、安装指南等辅助文档；技能只保留 Agent 完成任务需要的信息。

### 3. 写 frontmatter

```markdown
---
name: skill-name
description: 做什么 + 什么时候用 + 触发词 + 不适用场景。
---
```

约束：

- name 用小写字母、数字、连字符，与目录名一致。
- description 是唯一的常驻触发器：写清能力、典型任务和边界，不要写步骤。
- 描述可以稍微主动，但不要宽到抢别的技能，也不要窄到永远不触发。
- 触发词写用户可能真的会说的词；不要只写内部术语。

### 4. 写正文

推荐顺序，可按任务删减：

1. **何时使用 / 何时不要用**：帮助命中，也帮助避让。
2. **核心判断**：3–5 条，回答「为什么这样做」「冲突时怎么选」。
3. **前置与输入**：需要读什么、确认什么、缺什么要先问。
4. **流程**：分阶段、动词开头；每一步说明产出和检查方式。
5. **分支/决策**：不同情况怎么选，什么时候停下来问。
6. **一个强对比示例**：好做法 vs 常见错误，短而具体。
7. **完成检查**：能逐项判断通过/不通过。
8. **常见反模式**：模型最容易偷懒或走偏的地方。
9. **安全边界**：不可信内容、权限、外部动作。
10. **与其他技能的配合**：避免重复和冲突。

### 5. 写清楚停止条件

技能不只告诉 Agent「做什么」，还要告诉它：

- 什么算完成。
- 什么情况必须停下来问用户。
- 什么情况应该换方案，而不是硬撑。
- 哪些捷径绝对不能用（跳过测试、伪造数据、绕过审批等）。

## 写作规则

- **具体优于正确**：不写「保证质量」，写「运行 typecheck/test/build，检查退出码和失败数」。
- **流程优于口号**：说明先做什么、后做什么、为什么；清单只作为检查，不代替流程。
- **判断优于罗列**：冲突时怎么取舍，比多列十条规则更有用。
- **短句、动词开头**：一条规则只做一件事。
- **可验证**：每一步都能判断通过/不通过；不能验证的规则不要写。
- **有边界**：写清不做什么、不能碰什么、什么情况问用户。
- **不重复**：同一原则只写一次；跨技能引用名称，不要复制两份。
- **示例要短**：一个具体好坏对比，胜过五段抽象解释。

## 触发设计

- description 里写 2–3 个典型场景和用户可能说的词。
- 写「何时不要用」，避免和相邻技能抢任务。
- 不要用「帮助处理所有 X 问题」这种过宽描述。
- 不要把某次任务的路径、函数名、变量名写死。
- 修改 description 后，重新做一次正向、负向和模糊触发测试。

## 测试技能

技能写完不等于有效。至少做四类测试：

1. **基线测试**：没有技能时模型会怎么做？记录具体失败模式。
2. **触发测试**：
   - 正面：典型请求是否想到这个技能？
   - 负面：不相干的小任务是否不会误触发？
   - 模糊：边界请求是否在需要时触发，而不是一律触发？
3. **压力测试**：时间紧、任务看起来简单、用户催促时，模型是否仍遵守关键步骤？
4. **对比测试**：有/无技能的输出差异；是否更完整、更可验证、更少返工？

失败时先判断是「没触发」「步骤不清」「规则被合理化绕过」还是「技能太长没读完」，再针对性修改；不要为了一个测试把技能写成过度具体的脚本。

## 修改现有技能

- 先读当前版本，确认真实问题：不触发、太长、步骤太泛、和别的技能冲突。
- 保留有效部分，做最小改动；不要整篇重写导致已有使用习惯失效。
- 更新 description 后同步测试触发；更新步骤时检查依赖的命令/工具是否仍存在。
- 用户改过的技能不要被升级覆盖；内置技能升级只更新未修改的副本。
- 需要版本记录时，在末尾写简短 changelog，不要单独建 CHANGELOG.md。

## 安装位置

- 用户技能：技能库目录，重新扫描后生效；可在技能库面板启停、删除、查看。
- 工作区技能：工作区的 .morrow/skills、skills 或 .skills 下，项目内生效。
- 内置技能：随应用安装；用户修改过的副本不升级，删除后不自动恢复。
- 重名时工作区优先；冲突要说明。
- 不要直接改应用安装目录里的内置技能；改用户技能或工作区技能。

## 技能模板

```markdown
---
name: my-skill
description: 做什么。当用户提到 A、B、C，或需要完成 D 时使用；不适用于 E。
---

# 技能标题

## 何时使用
- ...

## 何时不要用
- ...

## 核心判断
- ...

## 流程
### 1. ...
- 产出：...
- 检查：...

### 2. ...
- ...

## 示例
- 好：...
- 弱：...

## 完成检查
- [ ] ...

## 常见反模式
- ...

## 安全边界
- ...

## 与其他技能的配合
- ...
```

## 常见反模式

- **把技能写成文章**：背景很多，没有可执行步骤。
- **只写原则**：没有顺序、检查和例子，模型只能自由发挥。
- **触发描述太宽/太窄**：抢任务或永远不触发。
- **复制官方文档**：没有判断和取舍，遇到边界就失效。
- **过度具体**：把一次任务的路径/变量写死，换个项目就不能用。
- **上下文浪费**：重复系统提示、解释常识、塞长资料。
- **没有测试**：不知道是否触发、是否有效、是否被绕过。
- **和别的技能大量重复**：维护两份互相矛盾的规则。
- **忽略安全边界**：技能里的命令/外部内容被当成授权。
- **把技能当权限**：技能不能扩大工具、工作区或审批边界。

## 交付

说明技能名、触发场景、核心步骤、测试方式、安装位置和已知限制。不要只贴一份 SKILL.md 就结束。
