# 技能编写：把可复用的判断写成可执行的流程

## 何时使用

- 用户要求创建、修改、优化一个技能（SKILL.md）。
- 团队有重复出现的流程、规范或判断标准，需要沉淀给 Agent。
- 现有技能触发不准、步骤太泛、经常被忽略或执行走样。
- 需要把一次成功的工作方法抽象成可复用流程。

## 何时不要用

- 一次性任务：不值得沉淀。
- 能用脚本/校验/模板强制执行的规则：优先自动化，不要写成文档靠模型自觉。
- 项目专属约定：写进项目说明/AGENTS.md，而不是通用技能。
- 只是复制官方文档：技能应提供判断和流程，不是资料堆砌。

## 先判断是否值得写

值得写：

- 需要判断、取舍、顺序和验收的流程。
- 同一个问题会反复出现，且新手容易做错。
- 有明确的触发场景和可观察的完成标准。
- 能显著减少来回沟通或返工。

不值得写：

- 一句话能说清的规则。
- 纯粹的文件格式说明（除非有复杂决策）。
- 已经由工具/schema/校验强制的约束。
- 只适用于当前这一个任务的细节。

## 技能的结构

~~~text
skill-name/
├── SKILL.md          # 必需：frontmatter + 流程
├── references/       # 可选：长参考资料
├── assets/           # 可选：模板、图片
└── scripts/          # 可选：可复用脚本（Morrow 的技能安装器目前只接受文本/资源，不接受可执行脚本）
~~~

Morrow 的技能安装器只允许 Markdown、文本、JSON/YAML/CSV 和图片，不允许 .js/.py/.sh/.exe 等可执行文件。因此内置技能应该是纯 Markdown；需要脚本时，在技能里描述命令，让 Agent 用工作区内的脚本工具执行，而不是把脚本打包进技能。

## Frontmatter

~~~markdown
---
name: skill-name
description: 做什么 + 什么时候用 + 触发关键词。要让模型在合适的场景主动想到它。
---
~~~

约束：

- name：小写字母、数字、连字符；与目录名一致；不超过 64 字符。
- description：一句话到一小段；包含「能力」与「触发场景」；可写用户可能说的词。
- 不要在 description 里写步骤；步骤放正文。
- 描述要稍微「主动」：如果任务明显匹配，鼓励模型读取技能，而不是等用户点名。

## 正文结构

推荐顺序：

1. **何时使用 / 何时不要用**：帮助触发和避免误用。
2. **核心原则**：3–5 条，回答「为什么这样做」。
3. **输入/前置**：需要读什么、确认什么。
4. **流程**：分阶段、可执行步骤，每步有检查。
5. **决策树/分支**：不同情况怎么选。
6. **示例**：一个具体的好例子 + 一个弱例子。
7. **检查清单**：完成前逐项确认。
8. **常见反模式**：新手最容易犯的错。
9. **安全边界**：不可信内容、权限、外部动作。
10. **与其他技能的配合**：避免重复，形成体系。

## 写作原则

- **具体优于正确**：不要写「要保证质量」，写「运行 typecheck/test/build，检查退出码和失败数」。
- **流程优于清单**：清单是检查项，流程要说明先做什么、后做什么、为什么。
- **判断优于口号**：告诉模型在冲突时如何取舍，例如「先保证主路径可用，再做视觉打磨」。
- **短句、动词开头**：一条规则只做一件事。
- **可验证**：每一步都能判断通过/不通过。
- **有边界**：写清不做什么、不能碰什么、什么情况停下来问。
- **不重复**：同一原则只写一次；需要时引用其他技能。
- **控制长度**：正文尽量 100–250 行；超过 300 行考虑拆分或放 references。Morrow 单文件技能建议不超过 500 行。

## 触发设计

- 在 description 里写用户可能说的词：审查、review、调试、报错、报告、发布说明、表格、PPT、网页、海报等。
- 写「何时不要用」，避免和相邻技能抢任务。
- 给 2–3 个典型触发场景，不要只写抽象能力。
- 避免过宽的描述（「帮助处理所有代码问题」），否则会抢别的技能。
- 避免过窄（只写一个内部函数名），否则永远不触发。

## 测试技能

技能也需要测试，不是写完就发。

### 1. 基线测试

找一个没有该技能时会做错的场景，记录 Agent 的默认行为（例如：不运行测试就说完成、只做居中卡片、直接猜根因）。

### 2. 触发测试

- 正面：用户说「帮我审查这个 PR」「这份报告要发给客户」时，技能是否被想到？
- 负面：用户说「修个错别字」时，是否不会误触发大型流程？
- 模糊：用户说「看看这个页面」时，是否在需要时触发，而不是一律触发？

### 3. 压力测试

给 Agent 一个容易偷懒/走捷径的场景（时间紧、任务看起来简单、用户催），看它是否仍遵守关键步骤。技能里的「红旗/自我辩解」部分就是为这种情况准备的。

### 4. 评估与迭代

- 对比有/无技能的输出：是否更完整、更可验证、更少返工？
- 收集失败模式：是没触发、步骤不清、还是规则被合理化绕过？
- 针对失败模式改技能：补触发词、补判断标准、补反例、补停止条件。
- 不要为了让一个测试通过而把技能写成过度具体的脚本。

## 修改现有技能

- 先读当前版本和使用记录，确认问题：不触发、步骤太泛、太长、和别的技能冲突。
- 保留有效的部分，做最小改动；不要整篇重写导致用户已有的使用习惯失效。
- 更新 description 时同步测试触发；更新步骤时检查依赖的工具/命令是否仍存在。
- 记录版本变化（可在技能末尾加简短 changelog）。

## 安装与更新

- 用户技能：放在技能库目录，重启/重新扫描后生效；可在技能库面板启停、删除、查看文件。
- 工作区技能：放在工作区的 .morrow/skills、skills 或 .skills 下，项目内生效。
- 内置技能：随应用安装；用户修改过的副本不会被升级覆盖；删除后不会自动恢复。
- 重名时，工作区技能优先；同名冲突要说明。
- 不要直接修改应用安装目录里的内置技能；改用户技能或工作区技能。

## 常见反模式

- **把技能写成文章**：讲了一堆背景，没有可执行步骤。
- **只写原则**：没有顺序、检查、例子，模型只能自由发挥。
- **触发描述太宽/太窄**：抢任务或永远不触发。
- **复制文档**：没有判断和取舍，遇到边界就失效。
- **过度具体**：把一次任务的路径/变量写死，换个项目就不能用。
- **没有测试**：不知道是否触发、是否有效、是否被绕过。
- **和别的技能大量重复**：维护两份互相矛盾的规则。
- **忽略安全边界**：技能里的命令/外部内容被当成授权。

## 交付

说明技能名、触发场景、核心步骤、测试方式、安装位置和已知限制。不要只贴一份 SKILL.md 就结束。
