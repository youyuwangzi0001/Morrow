# 前端艺术指导：让成品有明确的世界，而不是模板

## 何时使用

- 从零制作网页、游戏、海报、报告页、单文件 HTML 视觉成品。
- 用户要求「好看 / 惊艳 / 高级感 / 有氛围 / 像作品 / 不要模板感」。
- 打磨既有界面：统一风格、修正层级、间距、状态、响应式和可访问性。
- 需要为一个产品/品牌建立可复用的视觉方向，而不是只调一张截图。

## 先判断场景

| 场景 | 规则 |
|---|---|
| 修改 Morrow 自身界面 | 必须沿用现有设计 token、组件和交互语言；不要引入第二套视觉系统 |
| 独立成品（报告、海报、游戏、落地页） | 可以建立新的视觉世界，但必须与主题、受众和内容一致 |
| 既有品牌/模板 | 品牌规范优先；没有规范时，从内容中提炼方向 |

## 核心原则

**审美不是功能完成后的装饰，而是用户对成品的第一判断。**

**高级感来自一致性和克制，不来自特效数量。** 一个明确的世界观、一个视觉焦点、一套稳定的字体/颜色/间距规则，比堆十种渐变更有说服力。

**结构也是信息。** 边框、编号、分隔线、标签、刻度，只有在表达内容关系时才使用；不要为了「设计感」给所有内容加装饰。

## 第一步：写视觉简报

不要直接写第一行 HTML。先用几句话确定方向：

1. **世界**：这是什么装置、刊物、场所或系统？例如「轨道训练舱的控制台」，而不是「一个深色游戏页面」。
2. **受众与任务**：谁看、在什么设备上看、第一眼要理解什么。
3. **情绪温度**：冷峻、神圣、破败、精密、怀旧、温暖、危险等，选最贴切的词。
4. **参考锚点**：具体的年代印刷、工业设计、电影美术、艺术运动、材料工艺。不要写「现代简约」这种空词。
5. **唯一视觉焦点**：首屏第一眼必须看到什么？巨大字标、主舞台、核心装置、一张关键图，而不是平均分布的卡片。
6. **设计 token**：颜色角色、字号层级、间距节奏、圆角/描边规则、材质与阴影。先写进 CSS 变量，再写布局。

简报控制在半页以内。没有简报就开始写，通常会在第三屏失去方向。

## 第二步：两轮设计

### 规划轮

- 用一段话和 ASCII 线框比较 2–3 个构图方向，不要直接实现第一个想法。
- 选一个方向，说明为什么它适合这个主题，而不是另一个。
- 写出 token 草案：4–6 个底色/材质色、强调色、状态色；2–3 个字体角色；间距与圆角规则。
- 检查：如果换成另一个同类主题，这套方案是否也成立？如果成立，说明它太通用，需要更具体。

### 工艺轮

- 先搭主舞台和第一屏，再补侧栏、状态、说明和底部信息。
- 统一字体层级、颜色关系、材质光影、间距节奏。
- 加一套克制的细节（接缝、刻度、状态灯、序列号等），每类规则只出现一次。
- 最后做减法：去掉一个不服务于主题的装饰。

## 构图：避免「居中卡片 + 大片空白」

- 把页面当成一张海报或一台机器：背景层 → 外框/机身 → 主舞台 → 侧边信息区 → 底部状态栏。
- 主舞台占视觉中心，但不一定在正中央；用非对称侧栏、刻度、标签和细线建立平衡。
- 信息密度要有节奏：巨大展示字、中等标题、微小技术参数并存；不要所有文字一样大。
- 首屏布置多个互补信息区：主视觉、当前状态、队列/预览、操作说明、遥测/统计。让画面像真实系统，而不是 demo 骨架。
- 标题屏本身要像一张海报：字标、副标题、任务说明、主操作、操作图例和状态灯齐全，不要只放一个按钮。
- 响应式不是把桌面缩小：窄屏优先保留主舞台和主操作，把侧栏折叠成横向状态条或底部抽屉；触控目标足够大。

## 字体

- 在系统可用字体里建立角色：窄体/压缩无衬线做展示字，几何或人文无衬线做正文，等宽字体做参数与数字。
- 展示字收紧字距，微标签放大字距，数字用 tabular-nums。
- 正文行宽控制在约 60–80 个字符；衬线正文行高略大。
- 不要在标题里只给一个词换斜体/颜色来制造重点；用字号、位置、留白和对比建立层级。
- 不要默认给每个标题加全大写小标签；只有当它真的表达分类/序列时才用。
- 字体必须能在目标环境使用：成品离线打开时不要依赖外部 CDN 字体；必须用时提供回退栈或内嵌。

## 颜色与材质

- 大面积低饱和底色、中面积材质色、少量高亮强调；避免纯黑和纯白，暗部保留色相。
- 按角色定义颜色：底色、表面、文字、弱文字、强调、成功、警告、危险、聚焦。
- 金属用多层斜面/内阴影/细噪点；玻璃用低对比反光；纸张用暖白和纤维纹理。不要所有表面共用同一种渐变。
- 对比度优先：装饰性低对比可以，正文和关键操作必须清晰。
- 深色和浅色主题分别检查，不要只反转颜色。

## 动效

- 一个主运动（背景漂移、仪表指针、扫描线、启动序列）配合少量交互反馈。
- 动效要解释状态变化：展开、确认、切换、加载；不要无意义地让每个卡片浮动。
- 支持 prefers-reduced-motion；提供关闭或减弱选项。
- 游戏音效优先用 WebAudio 合成，默认静音或首次交互后开启，并提供静音开关；不依赖外部音频文件。

## 文案

- 文案是设计内容，不是装饰。先问「这个界面需要说什么」，再决定怎么写。
- 用用户能理解的语言命名功能，不用内部实现术语。
- 按钮写会发生什么：「保存更改」「发布」，不要写「提交」。
- 错误说明发生了什么、怎么修；空状态给出下一步行动。
- 语气与品牌一致，但不要为了「高级」写得含糊或故弄玄虚。

## 常见「AI 模板感」检查

以下不是绝对禁止，但如果你的方案和主题无关、只是默认选择，就换掉：

- 暖米色背景 + 高对比衬线标题 + 陶土色强调。
- 近黑背景 + 单一荧光绿/朱红强调 + 发光渐变。
- 报纸式细线大标题 + 零圆角 + 密集多栏。
- 所有内容切成等宽等高的圆角卡片，统一阴影，靠渐变填充空白。
- 每个标题上方都有全大写小标签；元信息用中点连接；按钮都加箭头。
- 用 emoji 当图标、用外部 CDN 图片/字体、把占位符留给用户。
- 只有静态首屏，没有 hover/focus/disabled/空/错误状态。
- 为了「高级」降低对比度，导致文字看不清。

## 既有界面打磨

1. 先读现有 token 和同类组件（颜色、字号、间距、圆角、动效），不要引入冲突的视觉语言。
2. 列出状态：默认、悬停、焦点、按下、禁用、加载、空、错误、长文本、窄宽度、明暗主题。
3. 检查层级与密度：信息主次、对齐、留白、滚动区域、固定元素是否遮挡输入框或操作。
4. 可访问性：键盘可达、可见焦点、aria-label/role、对比度、减少动效。
5. 文案：简体中文、动词开头、避免术语堆砌；破坏性操作明确后果。
6. 实现后用真实界面验证：宽屏与窄屏、明暗主题、关键交互与回归；用截图作为证据。

## 功能与视觉双验收

1. 先保证逻辑：游戏规则、状态机、开始/暂停/结束/重开、键盘与触控、边界条件。用可重复的脚本或浏览器实测验证。
2. 再做视觉检查：首屏焦点、层级、对齐、留白、溢出、对比度、明暗主题。
3. 按需打磨：先做构图检查（焦点、信息密度、空白利用）和工艺检查（字体层级、颜色关系、材质光影、动效节奏）；只有发现具体弱点才进入下一轮并记录改了什么。已经达到验收线就直接交付，不要为了走流程固定追加轮次。
   - 构图轮：焦点是否够强？信息区是否像真实系统？空白是否被有效利用？
   - 工艺轮：字体层级、颜色关系、材质光影、动效节奏、微文案是否统一？
4. 如果环境支持截图，保存截图并检查画面本身；不要只看尺寸或代码。

## 常见反模式

- 深色 SaaS 仪表盘模板、紫色渐变光斑、玻璃拟态卡片堆叠。
- 只有一个居中标题和按钮，四周大片空白。
- 所有信息装进等高卡片，主次不分。
- 用留白掩盖内容不足，或为了「丰富」随机堆装饰。
- 第一版能跑就交付，没有视觉迭代记录。
- 只在桌面好看，窄屏溢出或交互不可用。

## 交付

最终答复先用一句话说清视觉概念，再说入口/玩法和验证结果。不要用「我加了渐变和阴影」当审美说明；说明你建立了什么世界、焦点是什么、用户第一眼看到什么、做了哪些真实检查。
