# 交付前验证：没有新鲜证据，就不说完成

## 何时使用

- 准备对用户说「已完成」「修好了」「测试通过」「可以交付」之前。
- 完成代码、文档、表格、报告、网页或任何成品后。
- 准备提交 Git、创建分支、结束目标或关闭计划之前。
- 用户质疑「真的能用吗」时。

这不是可选的收尾步骤，而是完成定义的一部分。

## 铁律

**没有运行验证命令，就不能声称它通过；没有打开成品，就不能声称它可交付。**

证据必须来自当前这轮真实的命令输出、文件内容、页面操作或截图，不能来自记忆、上次运行、代码看起来正确或子代理的口头保证。

## 验证闸门

在说任何完成类的话之前，依次做：

1. **确定证据**：哪条命令、哪个文件、哪次页面操作能证明这个说法？
2. **完整运行**：运行完整命令，不用「只跑一个用例」「只检查一半」代替。
3. **读取结果**：看退出码、失败数、错误信息、实际输出，不只看最后一行。
4. **对照断言**：输出是否真的支持你的说法？如果否，如实说明现状。
5. **再下结论**：只有证据成立时才说完成，并在回复里带上证据。

如果任何一步缺失，就不要使用「应该」「大概」「看起来没问题」这类词。

## 按成品类型验证

### 代码与工程

- 运行项目已有的 typecheck、单元测试、构建；有 lint 就一起跑。
- 修复缺陷时先复现：修复前失败、修复后通过；必要时临时撤回修复确认测试真的会失败。
- 检查调用方和旧数据兼容性；不要只验证新路径。
- 查看真实 diff，确认没有误改、调试残留、密钥和生成物。
- 无法运行完整测试时，说明原因，并给出可复现的最小验证步骤。

### 网页与 UI

- 在真实浏览器中打开，不只看代码或静态 HTML。
- 走通主路径：进入、操作、提交、返回、刷新；检查空状态、错误态、加载态。
- 检查窄屏（约 390px）、常规桌面和宽屏；检查深色/浅色主题。
- 检查键盘操作、焦点可见性、对比度和减少动效设置。
- 截图作为证据；截图要检查画面本身，不只看尺寸。
- 如果使用内置浏览器或画布，确认页面真实渲染、脚本执行、没有空白或错误页。

### HTML / Markdown / SVG 画布成品

- 用 open_artifact 打开，确认画布真实显示，而不是只有文件存在。
- HTML 要自包含：不依赖外网字体、图片或脚本；离线打开仍然完整。
- 检查滚动、宽窄屏、打印/PDF 预览、按钮反馈和空状态。
- 更新内容后重新打开同一产物，确认用户看到的是最新版，而不是旧缓存。

### Excel 与数据

- 用 write_xlsx 生成后重新读取，确认工作表、行列和公式存在。
- 公式必须是真公式（以 = 开头），不是手算后的常量；抽查合计、百分比和引用。
- 核对原始数据、口径、时间范围和清洗规则；确认没有覆盖原始文件。
- 关键数字至少用另一种方式复算一次；检查单位、空值、重复和异常值。
- 图表坐标轴、图例、单位和来源完整；不要把截断坐标轴伪装成从零开始。

### Word / PDF / PPT

- 生成或修改后用专用读取工具重新打开/解析，确认没有损坏、截断或空白页。
- 检查标题层级、分页、表格、图片、页码、目录和占位符。
- Word 修改必须输出到新文件，原文件保留；确认替换没有破坏样式。
- PDF 检查页数、文字可选中、图片清晰、链接可点。
- PPT 一页一个核心信息；远看标题和数字能读清。
- 没有生成能力时，交付 Markdown/HTML 并说明限制，不要伪造 .docx/.pptx/.pdf。

### 研究、报告与引用

- 每个关键结论有来源；优先一手资料，交叉核对至少两个独立来源。
- 记录 URL、标题、日期和访问时间；区分事实、推断和未知。
- 数字能追溯到文件或命令；引用能定位到原句，不把摘要当正文。
- 找不到可靠来源时明确写局限，不编造。

### Git 与发布

- 提交前看 git status 和 diff，确认只包含本次改动。
- 不提交密钥、用户数据、构建产物、缓存和临时文件。
- 提交信息说清为什么改；提交后确认工作区状态。
- 不重写已发布历史，不强制推送；破坏性操作先征得同意。
- 发布说明来自真实提交，不把计划写成已发布。

## 缺陷修复的验证

真正的回归验证是红-绿循环：

1. 写一个能复现缺陷的测试，运行并看到它失败。
2. 修复实现，运行同一个测试，看到它通过。
3. 再跑相关测试和构建，确认没有引入回归。
4. 如果没有自动化测试，记录手动复现步骤和修复前后的观察结果。

只写了一个测试但没有看它失败，不能证明它真的覆盖了缺陷。

## 完成声明模板

在最终回复里，用简短、具体的证据说明：

~~~text
已验证：
- npm run typecheck：0 error
- npm run test:unit：816 passed + 5 skipped
- 真实页面：390px / 1440px 下主路径可操作，深色/浅色截图已检查
- 生成文件：out/report.html 已打开，表格和图表完整

未验证/限制：
- 没有真实打印机，只做了打印预览
- 外部 API 未连接，使用本地 mock 验证了错误路径
~~~

不要把工具日志整段贴给用户；只保留能证明结论的关键行。

## 红旗与自我辩解

| 想法 | 现实 |
|---|---|
| 应该能跑 | 跑一遍再说话 |
| 我刚才改完，肯定没问题 | 改动之后必须重新验证 |
| 只跑了一个测试，够了 | 相关测试和构建都要跑 |
| 子代理说完成了 | 独立检查产物和 diff |
| 上次通过过 | 这次改动可能破坏它，重新跑 |
| 代码看起来对 | 代码正确不等于功能可用 |
| 我太累了，先交 | 疲惫不是跳过验证的理由 |
| 只改了一行，不用测 | 一行也可能改坏关键路径 |
| 页面截图看起来正常 | 还要检查交互、错误态和窄屏 |

## 常见反模式

- 用「已完成」代替结果路径和验证命令。
- 只跑 happy path，不检查错误、空状态、权限拒绝和取消。
- 用 sleep 或重试掩盖不稳定的测试，而不是定位原因。
- 为了让测试变绿而修改断言、跳过用例或降低校验。
- 用子代理的总结代替自己的验证。
- 交付打不开的文件、只有占位内容的页面、没有公式的「Excel」。
- 把计划中的功能写进发布说明。
