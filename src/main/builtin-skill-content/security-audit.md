# 安全审计：围绕信任边界找可复现的风险

## 何时使用

- 用户要求安全审查、上线前检查、渗透测试（在授权范围内）。
- 功能涉及外部输入、文件系统、命令执行、网络、凭据、权限或 MCP。
- 需要评估一个补丁是否引入新的攻击面。
- 需要给团队一份按严重程度排序的安全问题清单。

## 何时不要用

- 普通代码审查、性能优化：走 code-review。
- 未授权的真实系统测试、破坏性攻击、拒绝服务：拒绝，并说明边界。
- 需要访问真实用户数据/生产密钥才能验证：先获得明确授权，否则只做静态审计。

## 授权与边界

- 只做用户明确授权的范围；不确定时先问。
- 默认只读：不修改代码、不写数据、不发送外部请求、不进行破坏性测试。
- 需要 PoC 时，只在本地/隔离环境，使用测试数据，不攻击真实服务。
- 不读取、复制或外泄真实凭据、用户数据、生产日志。
- 发现高危问题时，先私下报告给用户，不在公开渠道披露细节。

## 第一步：画信任边界

列出：

- **资产**：用户数据、密钥、文件、账号、支付、系统权限、模型上下文。
- **角色**：用户、模型、网页、MCP server、插件、子代理、外部 API。
- **入口**：UI 输入、文件上传、URL、剪贴板、IPC、命令行、网络请求、MCP 返回值。
- **出口**：文件写入、命令执行、网络请求、消息发送、支付、权限变更。
- **边界**：哪些内容跨边界后仍然可信？哪些必须视为不可信数据？

关键问题：外部内容能否影响控制流、工具调用、权限判断或文件路径？

## 检查清单

### 注入

- 命令注入：是否拼接 shell 命令/参数；是否使用参数数组；是否经过 shell。
- SQL/NoSQL 注入：是否拼接查询；是否参数化。
- 模板/HTML 注入：是否把外部内容插入 DOM/HTML；是否转义。
- 日志注入：外部内容是否带换行/控制字符写入日志。
- 提示词注入：网页/MCP/文件内容是否被当作指令或授权。

### 路径与文件

- 绝对路径、..、符号链接、junction、盘符、UNC、大小写、Windows 保留名。
- 是否 realpath 后校验工作区边界；是否允许外部附件白名单。
- 上传/解压：zip-slip、文件数量/大小/深度限制、可执行文件类型。
- 下载：文件名清洗、目录限制、覆盖策略、部分写入。
- 删除/覆盖：是否备份、是否可回退、是否确认。

### 权限与审批

- 只读/聊天/计划模式是否硬拦截写入和执行。
- 审批能否被绕过（工具别名、子代理、脚本、MCP、浏览器）。
- 默认拒绝是否生效；权限档位是否与产品承诺一致。
- 子代理/集群是否继承权限，能否扩大。
- 会话级授权是否被错误复用。

### 凭据与隐私

- 密钥是否明文落盘、进日志、进错误信息、进提示词、进渲染层。
- 是否使用系统加密存储；导出/备份是否包含密钥。
- 日志/截图/错误报告是否脱敏。
- 是否有硬编码密钥、测试密钥、默认密码。

### 网络

- SSRF：是否允许访问内网/回环/云元数据；是否校验 scheme/host/port。
- 重定向：是否跟随到不允许的地址；是否校验最终 URL。
- 超时、响应大小、重试、限流；是否会被慢响应拖死。
- 证书错误是否被忽略；代理设置是否安全。

### 浏览器与 Electron

- contextIsolation、nodeIntegration、sandbox、preload 最小暴露。
- IPC 参数是否校验类型/路径/长度；是否只接受已注册频道。
- 自定义协议/CSP：是否允许内联脚本、远程资源、frame 嵌入。
- 外部链接是否交给系统浏览器；是否允许 javascript:/data:。
- WebContentsView/iframe 是否共享会话、Cookie、权限。
- 下载、弹窗、权限请求是否默认拒绝。

### MCP 与外部工具

- server 配置是否可信；stdio 命令/参数是否可被注入。
- OAuth/token 是否加密保存；是否泄漏给模型/日志。
- 工具 schema 与描述是否可能误导模型执行危险操作。
- 外部返回值是否被当作授权；是否有审批。
- 资源/提示词是否可能读取工作区外内容。

### 资源与稳定性

- 无界队列/缓存/重试；大文件/大响应；递归调用。
- 进程/定时器/监听器/句柄是否清理；取消是否真正中断。
- 权限提升、持久化、开机启动、计划任务是否经过确认。

## 验证与证据

- 对每个问题写清：位置、触发条件、影响、严重度、证据、修复建议。
- 能安全复现时给最小 PoC；不能复现时说明是静态分析结论。
- 区分「确定可利用」「需要特定条件」「理论风险」，不要把低危夸大成高危。
- 修复后验证：原 PoC 不再成立，同时没有破坏正常功能。

## 常见反模式

- **只扫依赖**：忽略业务逻辑、权限和路径。
- **把扫描器输出当结论**：不验证、不区分误报。
- **夸大低危**：为了显得有发现，把理论问题写成可利用漏洞。
- **忽略信任边界**：只检查输入格式，不检查输入能影响什么。
- **破坏性测试**：在未授权环境执行攻击、删除数据或打扰用户。
- **泄漏细节**：在公开回复里贴出可利用 PoC、密钥或用户数据。
- **修一个点**：不检查同类调用点和系统性原因。

## 与其他技能的配合

- 代码改动审查：code-review。
- 修复缺陷：debugging。
- 修复后验证：verify-before-delivery。
- 外部资料查证：web-research。
