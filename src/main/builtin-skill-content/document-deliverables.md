# 文档与成品：从真实材料到可打开的交付物

## 何时使用

- 写 README、使用说明、架构文档、技术规格、方案、提案、决策记录、发布说明。
- 做报告、汇总、汇报材料、幻灯片、白皮书。
- 修改或生成 Word、Excel、PDF、PPT 等办公文件。
- 用户要求「整理成一份能直接发出去的文档/报告」。

## 何时不要用

- 纯数据分析：先读 data-analysis，本技能负责最终呈现。
- 纯网页/游戏视觉：读 frontend-art-direction。
- 只是聊天回答，不需要文件成品：不要为了用技能而强行生成文档。

## 先确认六件事

1. **读者**：谁看？他们的背景、关心点、决策权限。
2. **用途**：阅读、评审、汇报、存档、发给客户，还是作为操作手册。
3. **格式**：Markdown、HTML、Word、Excel、PDF、PPT，还是多份组合。
4. **长度/深度**：一页摘要、完整报告、操作手册、演示大纲。
5. **材料来源**：工作区文件、用户提供的数据、需要联网查证的事实。
6. **完成标准**：必须包含哪些内容、不能出现什么、是否需要打印/演示。

信息不全时，先做合理假设并写明；只有影响交付方向的决策才问用户。

## 写作流程

### 1. 收集真实材料

- 读工作区里的源文件、数据、代码、旧文档和模板。
- 需要外部事实时先 web-research；不要把摘要当正文，不要编引用。
- 列出关键数字/结论的来源，确保每个都能追溯。
- 区分事实、推断、假设和待确认项。

### 2. 先搭结构，再写句子

默认结构：

1. 一句话结论 / 摘要。
2. 关键发现或方案（3–5 条）。
3. 证据、明细、图表、案例。
4. 方法、口径、限制。
5. 风险、待确认、下一步。

不同文体的调整：

- **README**：是什么 → 快速开始 → 核心概念 → 常见任务 → 限制/排障 → 参考。
- **技术规格**：背景/问题 → 目标与非目标 → 方案 → 接口/数据 → 失败与安全 → 迁移/回滚 → 验收。
- **决策记录**：背景 → 选项 → 决定 → 理由 → 影响 → 后续。
- **报告**：结论 → 发现 → 证据 → 方法 → 限制 → 建议。
- **发布说明**：版本/日期 → 新功能 → 改进 → 修复 → 破坏性变更/迁移 → 已知问题。
- **操作手册**：前置条件 → 步骤 → 预期结果 → 常见错误 → 回滚。

### 3. 写作规则

- 短句，先结论后细节；少形容词，多具体名词和数字。
- 每段只做一件事；标题写信息，不写「其他」「杂项」。
- 术语与产品 UI 一致；首次出现的缩写给出全称。
- 数字带单位、时间范围、口径；百分比说明基数。
- 表格列名清楚，右对齐数字，避免超宽；复杂表格配一句读法。
- 引用保留 URL、标题、日期；关键结论尽量给原文定位。
- 不写无法兑现的承诺；不确定的内容标注「待确认」。
- 破坏性操作/变更明确后果和迁移步骤。

## 格式与工具

### Markdown

适合 README、规格、说明、变更记录、轻量报告。

- 用 write_file 写入工作区；需要给用户看时用 open_artifact（kind=markdown）。
- 标题层级不要跳级；代码块标注语言；链接使用可点击路径。
- 长文档加目录；表格不要过宽。

### HTML 报告

适合需要版式、图表、打印/PDF 的报告。

- 单文件、自包含：内联 CSS/JS，不依赖外部字体/图片/脚本。
- 加打印样式：A4 页边距、避免标题孤立、表格不截断、页码/页脚。
- 用 open_artifact 打开；完成后在画布检查宽窄屏和打印预览。
- 详细视觉规范读 frontend-art-direction / canvas-artifacts。

### Word（.docx）

- 修改现有文档：read_docx 读取结构与占位符，edit_docx 复制到新文件并替换文字；原文件不动，输出路径必须不同。
- 新建文档：内置工具没有从零生成 docx 的能力时，先检查环境是否有 python-docx；用可复现脚本生成，再用 read_docx 重新读取验证。
- 保持样式：标题、表格、页眉页脚、编号；不要只替换文字却破坏结构。
- 交付前检查：段落数、表格、占位符是否残留、分页、图片。

### Excel（.xlsx）

- 用 read_xlsx 读取工作表和列名；用 write_xlsx 生成。
- 公式必须以 = 开头，写成真公式；不要手算后填常量。
- 多工作表命名清楚；汇总表注明口径；关键列加单位。
- 生成后重新读取，抽查公式、合计、空值和格式。
- 原始数据不覆盖；中间结果单独文件。

### PDF

- 读取用 read_pdf；扫描件/加密文件要先说明限制。
- 生成优先用 HTML + 打印/PDF 导出；也可用环境已有的库（如 weasyprint/reportlab），但必须先确认依赖。
- 交付前检查页数、文字可选中、图片清晰、链接可点、没有空白页/截断表格。
- 没有生成能力时，交付 HTML/Markdown 并说明如何导出，不要伪造 PDF。

### PPT（.pptx）

- 内置 read_pptx 只读；新建/修改需要 python-pptx 等环境能力，先检查依赖。
- 一页一个核心信息；标题写结论；图表优先于大段文字。
- 统一母版、颜色、字号、页脚；远看可读。
- 生成后用 read_pptx 或其他方式重新打开验证；没有能力时交付 HTML/Markdown 大纲，不伪造 pptx。

## 发布说明

- 来源：git log/diff、合并记录、任务清单；不要凭记忆编造。
- 分类：新功能、改进、修复、安全、破坏性变更、已知问题。
- 用用户视角写「做了什么 + 对谁有用 + 需要注意什么」，不要复述提交标题。
- 破坏性变更写迁移步骤；安全修复不暴露可利用细节。
- 版本号、日期、链接与代码一致；计划中的功能不要写成已发布。

## 文档自检

- 一个没参与项目的人能否按文档完成主任务？
- 结论是否在第一屏可见？关键数字是否有来源？
- 标题是否表达信息，而不是「概述」「其他」？
- 是否有占位符、TODO、示例数据未标注？
- 表格/图片/代码块是否溢出、截断、看不清？
- 链接是否可点、路径是否存在？
- 打印/PDF 是否分页合理、页眉页脚完整？
- 术语、单位、日期格式是否一致？
- 是否说明了限制、假设和未验证部分？

## 常见反模式

- 先写漂亮版式，后补内容，导致结构空洞。
- 把搜索结果/工具日志原样贴进文档。
- 编造数据、引用、版本号或发布日期。
- 生成 .docx/.pptx/.pdf 后不打开验证。
- Word 修改覆盖原文件，无法回退。
- Excel 用常量冒充公式，筛选/汇总一改就错。
- PPT 把文档按页切开，每页都是长段落。
- 发布说明把计划写成已发布。
- 文档只有 happy path，没有错误处理、限制和回滚。

## 交付

说明成品路径、格式、打开方式、内容范围、数据来源、验证结果和限制。需要用户确认的事项单独列出，不要藏在正文里。
