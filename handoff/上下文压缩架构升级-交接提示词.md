# 上下文压缩架构升级 · 交接提示词

> 用途：把「模型上下文」与「完整对话记录」拆成两层，实现「压缩后占用降到 10%–20%，且前端一条对话都不丢」。

## 交接提示词

### 背景

你在 Morrow（Electron + TypeScript，工作区 `C:\交付成品\Morrow`）里做一次**上下文压缩的架构升级**。

用户已经反馈并已修好两个压缩缺陷（见「已完成的前置工作」），但还剩一个结构性限制：

> 压缩后上下文占用降不下去（只降到 45% 左右），而且前端会丢失历史对话。

用户对比 Codex / Qoder 的体感：**每次压缩后上下文占用只剩 10% 以下，历史再密集也很少超过 20%；同时前端不会丢失任何对话内容。**

这个差距不是参数问题，是数据结构问题——请先理解这一节，再动手。

### 根本原因（必须先理解）

Morrow 目前只有**一份**消息数组，同时承担三个职责：

```
src/shared/types.ts:1088    Session.messages: ChatMessage[]
```

这一份数组既是：
1. 发给模型的上下文（API 的 `messages`）
2. 界面渲染的数据源（`src/renderer/store.ts`、`chat.tsx`）
3. 落盘 / 导出 / 搜索的唯一记录（`src/main/session.ts:542`）

核心运行时里同样是这一份：

```
src/core/agent.ts:2987    /** 工作副本：history + 本轮 user + 新增 assistant */
                          messages: ChatMessage[]
```

`maybeCompact()` 压缩时直接覆盖它：

```
src/core/agent.ts:5725    ctx.messages = applyCompaction(ctx.messages, plan.cutIndex, ...)
```

**于是「降低上下文占用」必然等于「删除界面上的历史对话」。** 压到 10% 就意味着删掉 90% 的对话记录——这正是体验差距的根源。

Codex / Qoder 的做法是**两份数据**：

| 层 | 用途 | 压缩行为 |
|---|---|---|
| 模型上下文 | 只发给 API | 激进裁剪到 10%–20% |
| 完整记录（transcript） | 界面、落盘、导出 | **永不删除**；压缩摘要作为一条标记插入 |

压缩是**本地**行为 + 一次模型摘要调用（不是云服务）。所以这个方案不依赖联网能力。

### 目标与验收

1. 压缩后，界面里的历史对话**一条都不少**；压缩处显示一条可展开的摘要标记。
2. 发给模型的上下文降到 `contextWindow` 的 **10%–20%**（目标比例可配置，默认建议 0.15）。
3. 长任务（数十轮工具调用）能连续多次压缩并继续跑完，不出现上下文溢出。
4. 落盘/导出/搜索看到的仍是**完整**历史。
5. 摘要按结构化章节撰写，保证压缩后能准确接续任务。
6. 旧会话（只有一份数组）升级后能正常打开、继续，不需要用户手动迁移。

### 建议的实施方案

**第 1 步：模型侧与显示侧分离（核心改动）**

- `RunContext` 增加模型侧数组，例如 `modelMessages: ChatMessage[]`；`messages` 保留为**完整历史**。
- `maybeCompact()` 只修改 `modelMessages`，**不再** `ctx.messages = ...`。
- 所有发给 provider 的地方改用 `modelMessages`（`stream()` 的 `messages` 参数）。
- 压缩时把摘要**追加**到 `ctx.messages` 作为一条标记消息（带 `preservedMessageIds`、轮次、节省量），而不是替换。
- `result.messages` / `compactedMessages` 语义调整为「完整历史 + 摘要标记」。

**第 2 步：事件与渲染契约**

- `messages_replaced`（`src/shared/types.ts:1685`、`src/main/agent.ts:5743`、`src/renderer/store.ts:1116`）当前含义是「用压缩结果替换界面消息」。拆层后它只应承载**完整历史**，不能让界面丢消息。
- 确认 `positionCompactionNotices()`（`src/shared/types.ts:1840`）仍能把摘要标记摆到正确位置。
- `CompactionNotice`（`src/renderer/features/chat.tsx:647`）已支持「第 N 次压缩 / 节省 xx tokens」的展开详情，保持它可用。

**第 3 步：目标比例**

- `src/core/agent.ts:519` 的 `targetRatio` 默认值从 `0.45` 收紧到 **0.15**（可配置）。
- 收紧后必须验证摘要质量：压得越狠，模型越依赖摘要。Morrow 已有结构化摘要（`composeCompactionSummary`，`src/core/compaction.ts:156`），需要实测确认接续质量。
- 注意 `RECENT_HISTORY_RATIO`（`src/core/agent.ts:402`，当前 0.25）与新 `targetRatio` 的关系：拆层后「近期历史」不再需要为保显示而留那么大预算，可按压缩质量重新评估。

**第 4 步：迁移与兼容**

- 旧会话仍是单数组。策略建议：读盘时原样当作「完整历史」，模型侧在首次运行时由完整历史重建（并立即按新比例压缩一次）。
- 检查所有读 `session.messages` 的地方口径是否仍是「完整历史」：
  - `src/main/session.ts:542/615/642/762/885/928`
  - 导出、搜索索引、artifact 版本同步（`getArtifactVersionStore().syncArtifacts`）
  - 分叉/回退（`applyRunResult` 附近的截断逻辑）

### 已完成的前置工作（不要重做，也不要回退）

1. **压缩触发改用真实 usage**：`planCompaction` 新增 `measuredTokens`，判定取「服务商实测」与「本地估算」的**较大值**。原因是本地估算按 CJK 1 字≈1 token，系统性偏低，曾导致界面显示 430.8k/400k（100%）却永不触发；而实测只是「上一次请求」快照，不能单独采信。接入点：`measuredContextTokens(ctx)`（`src/core/agent.ts:3066`）。
2. **压缩后保留近期历史**：新增 `RECENT_HISTORY_RATIO = 0.25`（`src/core/agent.ts:402`），切点搜索优先选「落进目标且保住近期历史」的位置；`keepsEnoughHistory` 只统计切点之后的 `keptTokens`（不要把 `preserved` 算进去，那会掩盖窗口被清空）。
3. **`overTarget` 语义**：从「超过 targetRatio」改为「压完仍逼近 `thresholdTokens`」，避免刚保住历史又被 `aggressiveTrim` 删掉。
4. **压缩轮次可追溯**：`planCompaction` 产出 `compactionRound`，`applyCompaction` 把轮次写进 header（`[历史对话摘要 · 第 N 次压缩 · 节省 xx tokens，任务继续]`），界面对应显示「上下文已压缩 · 第 N 次」。
5. **进度条来源标注**：`Usage.contextUsedSource: 'api' | 'estimate'`（`src/shared/types.ts:878`），`contextSnapshot()` 按该字段显示「精确 / 估算」，不再靠累计 inputTokens 反推。

### 必守约束

- **不要让第二个 Morrow 实例显现界面**（单实例锁相关，见 `src/main/index.ts:76`）。
- 不要把密钥、token、邮箱等敏感值写进摘要或日志；压缩后已有脱敏流程（`guard.redactMessage`），不要绕过。
- 不要在 `aggressiveTrim` 里删除消息来「让占用达标」——拆层后压缩只作用于模型侧。
- 保持 `estimatedTokens` 字段的「本地估算」原义（下游用它算节省量），实测值放在 `measuredTokens`。

### 环境注意（这台机器特有的坑）

- 构建要用可写临时目录，否则 esbuild 会失败：
  ```bash
  mkdir -p tmp/build-tmp && W=$(cygpath -w "$PWD/tmp/build-tmp")
  TMPDIR="$W" TMP="$W" TEMP="$W" npx electron-vite build
  ```
  原因：`os.tmpdir()` 可能被指到只读的运行时目录。
- 以管理员运行 Electron 需要 `--no-sandbox`。
- 指定数据目录用 `--data-dir=<绝对路径>`（`MORROW_DATA_DIR` 环境变量不用于此）。
- 工作区路径含中文，PowerShell 查进程时路径可能显示成短名，匹配时用唯一特征串而非完整路径。

## 附：为什么这个方案值得做

一句话总结给决策者：Morrow 现在的压缩是「用删除历史来腾空间」，所以占用降不下去、历史必然丢失；改成「模型上下文单独裁剪、完整记录永久保留」后，压缩比例可以放心压到 10%–20%，界面内容也不会少——这正是 Codex / Qoder 的体感来源，而压缩本身仍是本地行为，不需要云端服务。
