## 2. 本轮新增确认的十条功能断点

### N01 保存最终失败，正文分片却已经被改写（P1）

**用户会遇到什么：**程序说这次保存失败，旧工程文件也还在，但与它配套的正文分片已经变成新内容。再次打开时哈希对不上，又进入损坏恢复流程。

**复现：**先保存 26,000 字旧稿及快照；换成同长度新稿；在最后写 `project.json` 处注入磁盘失败。实测 `project.json` 完全未变，而 `part-0001.txt` 已改变。

**原因：**`save` 和 `savePassive` 先覆盖/删除正式分片，再做 JSON 容量检查与最终写入。单个 JSON 的原子写入并不能保证整套文件一起成功。该复现验证的是写入顺序与失败后结果，没有实际构造 512 MiB 工程或填满磁盘。

**修复验收：**分片使用新版本目录或暂存区，校验和所有可失败步骤完成后再切换工程引用；失败时旧 JSON 和旧分片必须一起保持有效。容量拒绝、分片写到一半、JSON 写入失败都应覆盖。依据：[分片写入](C:/交付成品/Morrow/src/main/studio.ts:467)、[保存顺序](C:/交付成品/Morrow/src/main/studio.ts:550)。

### N02 修复一个损坏章节，会连带回退其他完整章节（P1）

**用户会遇到什么：**第一章少了一块，打开后第二章刚保存的修改也退回旧稿。提示只说“正文分片不完整，已从最近历史版本恢复”，没有列明其他章节也被回退。

**复现：**保存含长第一章和“第二章旧稿”的快照；随后单独保存第二章新稿，不另建快照；删掉第一章一个分片，再打开。第二章实际回到旧稿。

**原因：**恢复整部历史工程，只合并最新素材、任务和交付记录，没有保留完整章节的新正文、其他元数据和画布等修改。另一个源码风险是隔离备份失败被吞掉，后面仍覆盖原工程，提示却声称原工程已保留。正常备份成功时新内容仍可能从 `corrupt-*` 找回，因此不能一概称为永久丢失。

**修复验收：**优先恢复损坏章节；如需全工程回退，应展示差异与回退范围并由用户选择。原数据隔离失败必须停止破坏性恢复，不能继续声称已经留备份。依据：[自动恢复](C:/交付成品/Morrow/src/main/studio.ts:427)。

### N03 人物阶段失败后，长篇蓝图重试会一直缺人物（P2）

**用户会遇到什么：**骨架成功、人物生成失败；按提示重试后，程序只接着写章节，最后又因缺人物失败，继续重试仍无法补齐。

**复现：**24,000 字、6 章蓝图：骨架返回合法数据，人物阶段返回不可解析数据。落盘草稿中的人物数为 0。重试的第一条请求直接要求“本批只写第 1–4 章”；两批章节完成后报“至少 2 位人物”。

**原因：**骨架一完成就写草稿；恢复时只要已有 `blueprint` 就跳过整个“骨架＋人物”分支。检查点没有区分人物步骤是否完成。

**修复验收：**分别记录骨架、人物、地点、各卷各批完成情况，重试先补缺失步骤；不能把“有骨架”当成“全部前置步骤已完成”。依据：[草稿恢复与人物分支](C:/交付成品/Morrow/src/main/studio.ts:8269)。

### N04 全书审稿漏掉长章尾部，却记录整章已经审完（P2）

**用户会遇到什么：**一章 9,000 字，后 1,000 字没有交给模型，检查页仍可显示这章已覆盖、审稿完成。

**复现：**正文前 8,100 字后加入唯一结尾标记，执行 `scope: all`；真实模型请求中没有该标记，受控返回无问题后，阶段为 `done`，覆盖为 1/1。

**原因：**全书批次按章分组，但每章仍只取前 8,000 字。当前章/自动抽样还有每章 12,000 字和总计 60,000 字上限，同样缺少章内覆盖记录。

**修复验收：**长章继续按段分批，记录实际阅读区间与原文版本；有任何区间未读，就不能把整章或全书算为完成。依据：[全书送审材料](C:/交付成品/Morrow/src/main/studio.ts:10842)、[完成声明](C:/交付成品/Morrow/src/main/studio.ts:11020)。

### N05 500 章全书审完，覆盖记录只留下最后 240 章（P2）

**用户会遇到什么：**全书任务称已审完，检查页却显示前半本还有大量未审；再次操作可能重复耗时和调用。

**复现：**将 500 章按实际规则构造成 125 个四章批次，全部同一原文版本，调用实际覆盖合并函数；结果只有最后 60 批，即第 261–500 章、240 章。

**原因：**覆盖列表无条件 `.slice(-60)`，把当前全书必需的有效覆盖当成可裁剪日志。本轮没有为此实际发起 125 次模型请求，结论来自生产合并函数与界面统计路径。

**修复验收：**当前有效覆盖按章/镜 ID 去重保存，历史展示可以分页；不得因日志条数限制丢掉当前覆盖。依据：[合并函数](C:/交付成品/Morrow/src/main/studio.ts:12693)、[界面未审计算](C:/交付成品/Morrow/src/renderer/features/studio.tsx:3487)。

### N06 审第二章，会清掉第一章仍有效的审稿记录（P2）

**用户会遇到什么：**逐章审稿时，前一章内容没有变，刚审完的记录却在审下一章后消失。

**复现：**先存第 1 章当前章覆盖，再合并第 2 章覆盖；实际只剩第 2 章。两次审稿的 `source` 因对象不同而不同。

**原因：**合并时要求同类型旧记录的 `source` 必须与本次完全相同，误把“审的是另一章”当成“旧章版本变了”。

**修复验收：**按对象 ID 与该对象版本判断有效性，只替换本次重审部分；第一、第二章依次审完应同时保留。依据：[覆盖过滤](C:/交付成品/Morrow/src/main/studio.ts:12701)。

### N07 分镜生成期间手改同一镜头，回来仍会覆盖人工修改（P1）

**用户会遇到什么：**开始重做第 5 镜后，又手动改动作或台词并保存；AI 返回时，将人工修改盖回基于旧稿的结果。

**复现：**在实际 `applyScopedStoryboard` 写回前修改原镜头动作和 `updatedAt`，保留镜头 ID；应用后人工动作被生成动作替换。

**原因：**生产任务直接调用该函数；它只检查原镜头 ID 是否仍存在，没有检查内容或开始时的版本。草稿续作的来源指纹只用于挑选检查点，不能替代最终写回冲突检查。小说润色已具备的保护没有覆盖到分镜。

**修复验收：**逐镜记录开始版本，写回时比对；冲突镜头保留为候选或要求比较确认，无冲突镜头可以继续采用。依据：[任务应用入口](C:/交付成品/Morrow/src/main/studio.ts:9442)、[ID 检查](C:/交付成品/Morrow/src/main/studio.ts:13721)。

### N08 当前章审稿失败，重试却改成自动抽样（P2）

**用户会遇到什么：**本来只审第 50 章，失败后点“重试”，实际审了第 1 章和末尾几章，第 50 章可能根本不在其中。

**复现：**两章工程选择当前第 2 章，故意让审稿返回无效数据；持久化的 `retry.payload` 是空对象。执行真实 `retry-job` 后，新任务从“1 章”变为“2 章”，实际请求包含两章。

**原因：**重试没有保存 `scope` 和 `chapterId`，重新调用后落入默认自动抽样分支。

**修复验收：**重试保留原范围与目标对象；若原文变化，需要说明采用新版本还是原快照，不能默默换对象。依据：[重试输入](C:/交付成品/Morrow/src/main/studio.ts:11055)、[重试执行](C:/交付成品/Morrow/src/main/studio.ts:7977)。

### N09 画布离开补存，把 A 的画布写进 B（P1，真实界面）

**用户会遇到什么：**在 A 添加一个文本节点，自动保存前立即从顶栏切换 B；A 的修改没保存，B 却被写入整张 A 画布。若 B 已有画布，还存在覆盖其内容的风险。

**复现：**先确认磁盘上 A 有 16 节点、B 为 0；脚本触发实际“文本”按钮和切换作品按钮；等待保存完成后读取工程，**A 仍为 16，B 变为 17**。没有通过测试 API 直接写这份画布。

**原因：**卸载清理触发 `persist`，但调用 `run('save-canvas', …)` 未带草稿所属作品 ID。此时 store 的 active 已变成 B，公共调用器按 B 发请求。新增补保存只解决了同作品换页面，没有锁定原作品。

**修复验收：**草稿、保存队列、卸载补存均固定所属作品 ID；切换、退出、保存失败和保存中再次修改都应验证 A/B 两边磁盘内容。时间线也存在未显式绑定作品 ID 的补存调用，应一并排查，但本轮没有把未实测的时间线串写列为另一个已确认问题。依据：[画布保存](C:/交付成品/Morrow/src/renderer/features/studio.tsx:1385)、[卸载补存](C:/交付成品/Morrow/src/renderer/features/studio.tsx:1415)、[默认目标](C:/交付成品/Morrow/src/renderer/features/studio-core.ts:889)。

### N10 成片已标过期，只因时间线版本号相同仍被选中（P2）

**用户会遇到什么：**换了配音或素材，系统已经提示需要重新装配/合成，但导出音轨仍能选到换素材前的旧视频。

**复现：**建立实际存在的视频文件，记录与当前时间线相同的版本号；调用实际素材变更失效逻辑后，timeline/delivery 均为 `stale`。`currentTimelineVideo` 仍返回这个旧视频。

**原因：**视频有 `timelineVersion` 时只比较数字；只有无版本元数据的旧交付才检查 stale。素材变化不一定立即增加时间线版本号。`exportAudio` 没有另外阻止这一状态，完整发布入口则还有额外预检。

**修复验收：**选当前成片时同时检查上游失效状态和渲染依据；更换配音/素材后，旧片可以作为历史版本显式选择，但不能冒充当前成片。本轮验证了源选择及调用链，没有实际重新编码音频。依据：[选择函数](C:/交付成品/Morrow/src/main/studio.ts:3124)、[素材失效](C:/交付成品/Morrow/src/main/studio.ts:6974)、[音频入口](C:/交付成品/Morrow/src/main/studio.ts:11157)。
