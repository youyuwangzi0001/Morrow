# B3 · 传输层（第一批：强制配对 + 长期密钥）

> B 轨最重的一张卡（2.5 人周）。完整 B3 含三级回退、seq 补漏、ring buffer、
> snapshot 降级。本轮先做**优先级最高的两块**：堵住 B2 留下的安全降级，
> 以及让配对在重启后仍然有效。

## 1. 为什么先做这两块

B2 报告 §7 列了 6 条限制，其中前两条是「功能看起来在、实际不可用」的类型：

| 限制 | 真实后果 |
|---|---|
| `pairing` 参数可选，不传即静默退化为无鉴权 | **生产环境等于没有鉴权** |
| 桌面长期密钥只在内存，重启即换 | 用户每次开电脑都要重新扫码配对 |

第二条直接让功能不可用（手机一直连不上）；第一条是安全漏洞。
两者都比「三级回退」更该先修 —— 传输层再漂亮，鉴权是假的也没有意义。

## 2. 缺陷确认：不是「可能会漏」，是已经漏了

先读真实代码，确认 `applyRelaySettings` 到底传没传 `pairing`：

```ts
// 修复前 src/relay/index.ts
handle = await startRelay({
  enabled: true,
  dataDir,
  port: settings.relayPort
  // ← 没有 pairing
})
```

而 `startRelay` 里的写法是：

```ts
if (pairing) { /* 校验 */ }   // 不传就整段跳过
```

所以 B2 的配对逻辑**在真实启动路径上一次都没执行过**。
B2 当时那 15 项接入测试全绿，是因为测试自己传了 `pairing` —— 这正说明
「测试通过」和「产品可用」是两件事。

## 3. 修复一：强制配对

不能简单地改成 `if (!pairing) throw`，因为 B1 的 netstat 验收需要无鉴权模式。

修法是**要求显式声明**：

```ts
if (!pairing && config.allowUnauthenticated !== true) {
  throw Object.assign(new Error('relay 拒绝启动：未提供 pairing…'), { code: 'PAIRING_REQUIRED' })
}
```

设计理由：想让通道裸奔，必须把 `allowUnauthenticated: true` 写出来。
写出来就会在 review 时被看到，而不是像「不传参数」那样自然地滑过去。

检查放在 `enabled` 判断**之前**：配置错误应该在启动配置阶段暴露，
而不是等用户打开开关时才炸 —— 更不能用「关一次再开」绕过。

`index.ts` 现在会构造并传入 `pairing`（`src/relay/index.ts:88`）。

## 4. 修复二：长期密钥持久化

新增 `src/relay/keystore.ts`（141 行）。三条约束：

**一、私钥落盘必须加密。** 用 Electron `safeStorage`（Windows 走 DPAPI，
绑定当前用户账户）。明文私钥落盘等于把「曾配对过的所有手机」的会话密钥
交给任何能读文件的进程。

**二、`safeStorage` 不可用时不能明文降级。** 有些 Linux 环境没有 keyring。
正确做法是**拒绝持久化**（返回临时密钥），而不是偷偷写明文 ——
那会在用户不知情的情况下降低安全性。测试 `safeStorage 不可用时不写明文文件`
专门锁住这条。

**三、写入用临时文件 + rename。** 直接写目标文件时若进程中途崩溃，
会留下半个文件，下次启动解析失败 → 又回到「重启要重配」。
`rename` 在同一分区上是原子的。

`PairingService` 构造函数新增 `privateKey` 参数，从磁盘还原后
`setPrivateKey()` 复用 —— 桌面公钥保持不变，已配对手机算出的 ECDH
共享秘密继续有效。

### 配对 HMAC 密钥从长期私钥派生，不单独落盘

```ts
sha256(`morrow-relay-pairing:${privateKey}`)
```

理由：多一个需要保护的秘密，就多一个泄露面。派生自同一个被 safeStorage
保护的私钥，重启后派生结果不变。

1. **未做 WSS / 加密传输。** 本轮只修鉴权与持久化；HTTP 报文仍是明文。

2. **三级回退未做**（LAN WSS → 中继 WSS → FCM + 拉取）。
3. **seq 补漏 / ring buffer / snapshot_required 未做。**
4. **已配对设备表未持久化。** 长期密钥持久化解决了「桌面公钥不变」，
   但设备表本身仍在内存 —— 重启后手机需要用长期密钥**重新认证**
   （不重新扫码），该流程属完整 B3。
5. **`ws` / `mdns` 两个依赖未安装。** 完整 B3 需要它们；
   本轮实现不依赖任何新依赖（纯 `node:crypto` + `node:fs`）。
6. **测试用的是假 safeStorage（XOR），不是真实 DPAPI。**
   假实现不改变密文长度、对同一明文产生同一密文；真实 DPAPI 有头部开销且每次不同。
   所以测试只断言「文件里不含明文私钥」，不断言密文长度或内容特征 ——
   真实的加密强度依赖 Electron `safeStorage`，本轮无法在测试环境里验证。
   这意味着**「落盘是密文」这条在本机只验证了流程，没验证密码学强度**。

## 9. 第二批：Envelope + ReplayBuffer

第一批修的是「鉴权」；这一批修的是**「不许丢消息」**。

### 9.1 为什么这两块要先做

蓝图 B3 的三条验收里，有两条不依赖任何网络传输：

| 蓝图验收 | 依赖 |
|---|---|
| 断网 30 秒后重连，事件不重不漏（seq 连续性脚本验证） | 纯逻辑 ✓ |
| ring buffer 溢出时正确返回 `snapshot_required` | 纯逻辑 ✓ |
| 关掉 mDNS 后 5 秒内降级到中继 | 需要真实网络 |

先做前两条：它们能在本机 100% 验证，而且**是后一条的基础**
（降级切换时同样要靠 seq 补漏说服自己「没丢东西」）。

### 9.2 交付物

| 文件 | 行数 | 职责 |
|---|---|---|
| `src/relay/net/envelope.ts` | 150 | 信封结构、严格校验、seq 分配器、连续性判定 |
| `src/relay/net/replay-buffer.ts` | 221 | 环形缓冲（2000）、补齐、`snapshot_required` 降级、客户端重连状态机 |
| `tests/unit/relay-net-replay.test.ts` | 309 | 21 项，覆盖蓝图验收 1 与 3 |

### 9.3 三个关键设计决策

**一、环形缓冲，不是「数组 + shift()」。**
`shift()` 在大数组上是 O(n)，每来一条事件就搬移 2000 个元素，
高频事件流下会明显卡顿。环形缓冲写入 O(1)，内存占用恒定 ——
不会因为应用开一整天而膨胀。

**二、溢出必须降级，绝不静默丢弃。**
这是本批最重要的一条。最容易做假的写法是：溢出后只把还留着的发过去，
客户端以为补齐了，实际中间少了一截 —— 用户看到「对话记录里少了几条」，
而且**永远不会自愈**。所以 `replay()` 一旦发现 `lastSeq` 早于缓冲起点，
直接返回 `snapshot_required`，让客户端重拉全量。

**三、跳号时 `lastSeq` 绝不推进。**
客户端收到 seq=15 但期望 11，说明 11–14 丢了。如果这时把 lastSeq 推进到 15，
那 11–14 就**永久丢失**（下次补漏从 16 开始要）。
所以 `receive()` 在跳号时只返回缺口信息、不推进状态，等补漏结果再说。

### 9.4 一个容易写错的边界

`replay()` 判断「能否补齐」的条件是 `lastSeq < oldest - 1`，不是 `lastSeq < oldest`。

- 若 `lastSeq === oldest - 1`：客户端收完了被挤出前的最后一条，
  缓冲里从 `oldest` 开始正好接得上 → **可以补齐**。
- 若 `lastSeq < oldest - 1`：中间确实缺了一截 → **必须降级**。

单测专门锁住这个边界（`lastSeq 恰好等于 oldest-1 时可以补齐，不该误报降级`）。
写错这一处会让用户在「刚好没掉队」时被迫重拉全量，白等几秒。

### 9.6 反向验证

| 注入的错误 | 结果 | 证明 |
|---|---|---|
| 溢出时不降级，只发还留着的（静默丢弃） | 2 项失败 | 「不静默丢弃」真的在检查 |
| 补漏时 off-by-one（`> lastSeq + 1`） | 3 项失败 | 「不漏」真的在检查 |

第二条值得说：off-by-one 让补漏少发第一条，是这类代码最常见的缺陷。
它同时被「不重不漏」「逐条投递」「边界补齐」三项测试抓到，
说明这几项测试不是重复断言同一个东西。

### 9.7 已知限制（本批）

1. **仍然是纯逻辑，没有接到真实传输上。** 没有 WSS、没有 mDNS、
   没有中继。本批只解决「协议正确性」，网络层属后续。
2. **seq 不跨进程持久化。** 进程重启后从 1 重新开始，客户端靠快照重新对齐。
   这是刻意的（见 `SeqAllocator` 注释）：跨进程持久化 seq 会让
   旧连接的迟到包与新连接混淆。
3. **缓冲是进程内内存结构**，不做磁盘持久化。Morrow 崩溃重启后
   所有缓冲丢失，客户端必须拉快照 —— 行为正确，只是重连成本略高。
4. **未实现背压。** 如果客户端消费慢而服务端生产快，当前会一直覆盖旧事件
   直到溢出（然后触发降级）。真实场景应加「发送队列水位」控制。

### 补完全部 26 条之后：有一条必须反过来拿掉

把 `app:open-external` 加进白名单后，B1 原来那条「危险通道都不在白名单里」
的测试立刻失败。起初我判断是测试过时了 —— 蓝图明明要放行它。

但顺着这条线索去核对桌面的真实实现（`src/main/ipc.ts:413`）：

```ts
if (!/^https?:\/\//i.test(url)) return fail('INVALID_URL', '只能打开 http(s) 链接。')
await openExternalUrl(url)   // 调用系统浏览器
```

而全仓搜索 `morrow://`，**没有任何深链处理器**。

也就是说：桌面这个通道的语义是「打开浏览器看网页」，
而蓝图对它要求的是「只能唤起桌面，不能唤起浏览器」——**两者正好相反**。
放行它等于给手机一个「让桌面打开任意网页」的通道，正是蓝图明令禁止的。

所以决定：**不放行**。等桌面侧真正实现 `morrow:` 深链后再启用。
`checkPayload()` 里的深链校验（含拒绝控制字符注入）已经写好，
届时把条目加回白名单即可直接生效。

这比「照着蓝图表格无脑补齐」更贴近蓝图的本意：
蓝图给的是**语义要求**（只能唤起桌面），不是「必须包含这个字符串」。
**只放行不做参数限制，等于放行了半个危险能力。**

`feature:studio:action` 是典型例子：蓝图只允许 `read` / `preview` 两个 type，
但通道名相同，payload 里的 `type` 可以是任何值。只按通道名放行，
等于把创作台的全部写操作都暴露给手机。

所以补了 `checkPayload()`：

| 通道 | 限制 | 不加会怎样 |
|---|---|---|
| `app:open-external` | 只允许 `morrow:` 深链 | 可让桌面打开任意 URL（当前未放行，校验逻辑备好） |
| `feature:studio:action` | 只允许 `read` / `preview` | 创作台的写操作全部暴露 |

并且**真的接进了 `server.ts`**（第五道判定），不是躺在 allowlist 里当死代码。
`relay-payload-gate.test.ts` 里 4 项发真实 HTTP 请求验证。

反向验证：把 `server.ts` 里的 `checkPayload` 调用去掉，
studio 越权与审计相关项立刻失败。恢复后全绿。

### 补完白名单后，又拿攻击输入探了一次

新写的 `checkPayload()` 自己也可能有洞。所以写了个探针，拿 13 种畸形 URL 去打它：

```
FAIL  应拒绝: "morrow://x\nhttps://evil.com" — 被放行了！
FAIL  应拒绝: "morrow://x\u0000https://evil.com" — 被放行了！
```

**两个真实绕过**：前缀校验只看 `morrow:` 是否合法，
但换行和 null 字节让一个字符串里塞进了第二个地址。
下游若按行或按 null 截断解析（很多 URL 解析器和日志系统会），
就会打开后半截那个恶意地址。

修法：在 scheme 校验**之前**先拒绝控制字符（`\u0000-\u001f\u007f`），
再加 2048 字符长度上限。修完 13 种畸形输入全部被拒，
而 `MORROW://`、`Morrow://` 这类大小写变体仍正常放行（不该误伤）。

对应的测试 `app:open-external 拒绝换行与 null 注入` 已固化为回归用例。
反向验证：把控制字符检查删掉，该项立刻失败 —— 恢复后 27 项全绿。

**这一条比白名单条数更重要**：清单写全了只是「功能完整」，
输入校验写对了才是「安全」。而校验代码的正确性，只能靠主动构造攻击输入去验，
不能靠「我觉得这样写应该没问题」。

### 11.2 这句话其实有两个要求

最容易只做前半：

| 要求 | 只做前半会怎样 |
|---|---|
| 5 秒内降级 | 时间上界。降太慢，用户断网后要卡十秒才看到提示 |
| **UI 只变 chip 文案** | 降级时若重建连接对象，已加载的消息、滚动位置、草稿全丢 —— 用户看到「界面闪一下，聊天记录空了」 |

所以把**传输状态**与**内容状态**分开：`sessionRevision` 只在会话内容真的变化时递增，
`moveTo()` 绝不碰它。这句话变成了可机器验证的断言：
`切通道不改变 sessionRevision`。

### 11.3 调试出来的一个真实计时缺陷

第一版宽限期从「**第一次探测失败**」起算。测试全红：

```
expected 'lan' to be 'relay'
expected '直连' to be '中继'
```

原因：mDNS 在两次轮询**之间**被关掉。假设轮询间隔 1 秒：

- t=0 探测成功 → 记 `directDownSince = null`
- t=1 探测失败 → 记 `directDownSince = 1`
- t=6 才满足 `downFor >= 5000` → **降级发生在关掉后 6 秒，违反 5 秒上界**

而且这个偏差随轮询间隔线性增长，间隔 2 秒就会变成 7 秒。

正确做法：从「**最后一次探测成功**」起算。这样无论轮询间隔多大，
「最后一次确定可达 + 5 秒」都是确定的**上界**。
改成 `directUpAt` 后相关项全绿（现 29 项）。

这个缺陷值得记下来，因为它在**只有单测、没有真实网络**的环境里也能暴露 ——
前提是测试按「时钟推进」建模，而不是「调用次数」建模。

### 11.4 一条比蓝图更严的约束：宽限期

蓝图只要求「5 秒内降级」，没说「一丢包不能立刻降」。但只探测一次就切的话，
chip 会在 lan/relay 之间抖动，比降级更烦。

所以加了 `graceMs`（默认 5 秒 = 蓝图上界）。单测里三条：
单次失败不降级、间歇失败不累积、`graceMs=0` 时立即降级（反证宽限期真的起作用）。

### 11.5 中继只转发密文

蓝图原文：

> 中继只转发密文，无法解密内容——这一点必须在设置页明确写给用户看，
> 否则「把工作区推给第三方服务器」会直接劝退。

这句承诺的技术前提是「中继上跑的确实是密文」。如果某个字段以明文发过去，
「无法解密」就成了空话。所以提供两个工具：

- `looksLikeCiphertext(bytes)`：能解析成 JSON 的判定为明文
- `requireCiphertext(bytes)`：明文直接抛错，拦在发送之前

以及 `envelopeMeta()`：发往中继时只带 `v/kind/seq/sessionId/at`，**不带 body** ——
body 里可能是代码、文件路径或用户输入。单测断言序列化结果里不含
「机密内容」与 `secret.docx`。

### 11.8 交付前审查：三个只在写接口时留下的毛病

按 deliverable-quality 复查，读到自己的 `channel.ts` 发现三处问题，都修了：

**一、两个只写不读的字段。** `switches`（累计切换次数）与
`lastFailureReason` 都被赋值，但**从没有任何地方读取**。
它们看起来像「有统计能力」，实际是死代码 —— 而且 `switches` 在 `start()`
与 `moveTo()` 里各加一次，同一个切换会被算两遍，即使将来接上 UI 也是错的。
直接删掉；`switchHistory()` 已经提供了完整的切换轨迹。

**二、宽限期的计时基准错了**（见 §11.3，已经修过并写了完整分析）。

**三、`relay-payload-gate.test.ts` 有极小概率 `fetch failed`。**
连跑 9 个测试文件时出现过一次：前一个用例的 relay 刚 `close()`，
端口还在回收态，下一个 `fetch` 直接被拒。
这不是产品缺陷，但**是测试的确定性缺陷** —— 一个会偶发红的测试比没有更糟，
因为下次真红时会被当成「又是那个偶发」。

修法：`call()` 里对连接级失败重试一次（间隔 50ms），
断言仍然看业务响应码。改完连跑 4 轮全绿（此前是 3 轮里红 1 轮）。

### 11.9 第二轮审查：探针查出两个真实缺陷

上一节是读代码发现的；这一轮换方法：**写探针主动去撞边界**，
特别是「我写的安全工具本身能不能被绕过」。

**缺陷一：base64 编码的明文被判定为「密文」。**

`looksLikeCiphertext()` 的初版只检查「是不是 UTF-8 明文 JSON」。
探针把 JSON 套一层 base64 发过去：

```
base64 明文判定为密文: true
```

于是「中继只转发密文」的承诺被一个 base64 绕过 ——
而开发者很容易误以为「我看不懂 = 加密了」。**base64 只是编码，不是加密。**

修法：先试 UTF-8；若像 base64/hex 纯文本就解码后再判一次。
补了两条测试（base64、hex 各一），另加一条「真随机字节仍判为密文」，
防止修得过头把正常密文也拦了。

**缺陷二：未连接时 `view().tier` 返回 `'push'`。**

```
{"tier":"push","chip":"未连接","sessionRevision":0,"offline":true}
```

`tier === 'push'` 同时表示「已经退到推送兜底」和「还没开始连接」——
两者在 UI 上完全不同（前者显示「仅推送」，后者显示「连接中」）。
调用方只看 tier 就会把启动阶段渲染成「已降级」。

修法：`tier` 类型改为 `Tier | null`，未连接时给 `null`。
类型上就分不开了，不需要调用方记得同时判 `offline`。

两条都做了反向验证：把 `tier` 改回 `?? 'push'` → 1 项失败；
把 base64/hex 解码判断去掉 → 2 项失败。

## 12. 第四批：设备表持久化

### 12.1 先确认缺陷是不是真的

上一批（B3 第一批）修了「桌面长期密钥持久化」，当时我在报告里写：

> **已配对设备表未持久化。** 长期密钥持久化解决了「桌面公钥不变」，
> 但设备表本身仍在内存 —— 重启后手机需要用长期密钥**重新认证**
> （不重新扫码），该流程属完整 B3。

这句话**把问题说轻了**。写探针实测：

```
第一次运行后：已配对设备数 = 1
             数据目录内容 = desktop-key.bin
重启后：     桌面公钥是否不变 = true
             已配对设备数 = 0
             requirePaired 抛错 = DEVICE_REVOKED

FAIL  设备表重启后仍存在 — 实际 0 台
FAIL  手机重启后能直接重连 — 必须重新扫码配对
```

所以真实情况不是「需要重新认证」，而是**每天都要重新扫码配对**。
「重新认证」听起来像是自动的，实际要人工干预 —— 这又是把风险说轻的一次。

### 12.3 三条安全约束

**一、必须加密落盘。** 设备表里存着每台手机的 `sessionKey`，
它足以伪造该设备的全部请求签名（见 `verifyRequest`）。
明文落盘等于把「冒充任意已配对手机」的能力交给任何能读文件的进程。

**二、`safeStorage` 不可用时不降级为明文。** 读不出就当作空表，
让用户重新配对 —— 宁可麻烦，也不能悄悄降低安全性。

**三、撤销必须立即落盘。** 这是最危险的一条：如果 `revokeDevice()`
只删内存不写盘，应用重启后那台被撤销的设备会从文件里「复活」，
**等于撤销从来没发生过**。用户的直觉是「我踢掉它了」，
而系统在下次启动时又把它请回来。

所以落盘集中在一个 `persist()` 方法里，配对与撤销都调用它 ——
避免「配对写了、撤销忘了写」这种遗漏。

### 12.4 为什么用钩子注入而不是直接依赖文件

`PairingService` 不直接 import `device-store`，而是接收
`{ load, save }` 两个函数。理由：

- 单测不用起临时目录就能测状态机本身；
- 明确「持久化是可选的」：不传就纯内存（B2 的行为），向后兼容；
- 让「设备表」与「文件格式」解耦 —— 将来换成 SQLite 也不用改 pairing.ts。

### 14.3 `probe()` 的语义：为什么不是「端口在听」

这是本批最重要的设计决定，写错会让**界面说谎**。

`DirectChannel.probe()` 判定为 `监听正常 && 至少一台已鉴权手机连着`。

若只看端口：

| 场景 | 只看端口 | 实际 | 用户看到 |
|---|---|---|---|
| 桌面刚启动，手机还没连 | true | 无连接 | 「直连」—— 但手机其实从中继来的 |
| 手机掉线 | true | 断了 | 「直连」—— 通道已经空了 |

代价是冷启动时会先落在 relay/push，等手机连上再升级到 lan。
这是**正确的顺序**：升级不套宽限期（`poll()` 里升级是「变好」，无抖动风险），
用户几乎无感，而绝不会看到「明明没连上却显示直连」。

### 14.4 两条安全约束

**一、每条连接的第一帧必须是 hello，用 B2 的 `verifyRequest()` 校验。**
没通过 hello 的连接不收任何事件 —— 否则同网段的任何人都能连上来看桌面的活动流。
关闭码 `4401`，让手机能区分「密钥错」和「网络断」。

**二、5 秒内不发 hello 就断开。** 没有这条，同网段任何人可以大量连接占位。

### 14.5 重连补漏：先写缓冲再发送

`broadcast()` 的顺序是 **写缓冲 → 发送**。反过来的话，如果发送过程中手机断线，
重连时它报的 `lastSeq` 会大于缓冲里的最新序号，`replay()` 判「已是最新」，
那条事件就永久丢了。

超出缓冲时回 `snapshot_required`，绝不「只发还留着的」假装补齐 ——
那会让手机永久少一段，且不会自愈。

### 14.6 轮询器三个必须做对的地方

**一、不重叠执行。** `poll()` 是 async 的，一次可能超过 1 秒。
用 `setTimeout` 链（上次完成才排下次）而不是 `setInterval`，
否则慢的时候会堆积并发 poll，各自读改写 `directUpAt`，宽限期计算就乱了。

**二、stop 后不再执行。** 用递增代号（generation）：在途 poll 结束时会发现
自己的代号已过期，不再排下一轮。没有这个，用户关掉开关后后台仍在探测。

**三、定时器 `unref()`。** 否则 Electron 主进程会被这个定时器拖住，
用户关窗口进程不退出。

### 14.10 关于「连接对象泄漏」这条发现的经过

第一次做反向验证时，我注入「`close` 时不从 `clients` 移除」，**20 项全过**。

原因是 `probe()` 检查 `readyState`，死 socket 不算「已连接」，
所以功能行为完全正确。但集合会随每次连接无限增长 ——
用户一天开关手机几十次，每个死连接都持有 socket 与缓冲区。

这类缺陷不会让任何测试报错，只会让应用越用越慢。
修法是**直接暴露 `connectionCount()` 并断言它归零**，
而不是靠 `probe()` 的间接证据。

## 15. 第六批：应用层端到端加密

### 15.1 为什么 TLS 不够

蓝图在 Tier 2 上写了一句很硬的话：

> 中继只转发密文，无法解密内容——这一点必须在设置页明确写给用户看，
> 否则「把工作区推给第三方服务器」会直接劝退。

TLS 做不到这件事。**中继就是 TLS 的终点**：它用自己的证书与两端分别握手，
明文在它手上，它当然能解密再转发。要兑现承诺，必须在 TLS 里再套一层
只有手机与桌面知道密钥的加密（`sessionKey`，B2 用 ECDH 协商）。

在此之前 `requireCiphertext()` 只是一个**守门员** —— 它检查「你发的东西看起来
像不像密文」。守门员能被 base64 绕过（已修，见 §11），但它根本不产生加密。
这个文件才产生。

### 15.3 四个安全决定

**一、双向密钥分离。** phone→desktop 与 desktop→phone 用不同密钥。
共用一把的话，攻击者可以把手机发来的帧**原样反射**回去，
桌面会把它当成合法指令执行 —— 经典反射攻击。

**二、每连接一个 salt（16 字节）。** 重连时计数器从 0 开始。
若密钥不变，新连接的 counter=0 会与旧连接撞上同一个 GCM nonce ——
**GCM 下重用 nonce 直接泄露明文异或值**，是密码学级灾难。
所以服务端在 welcome 里下发随机 salt，参与密钥派生。

**三、AAD 绑定方向 + deviceId + salt + 计数。** GCM 认证 AAD 但不加密它。
把这几项放进 AAD：篡改方向（把手机帧当桌面帧）、跨设备挪用
（A 设备的密文挂到 B 设备名下）、改计数（重排），认证都会失败。

**四、计数器严格单调，解密成功才推进。** 先推进再解密的话，
攻击者用一个伪造帧就能把合法帧全部挤掉（先污染窗口再拒绝真消息的 DoS）。

### 15.4 抓到并修掉的一个真实漏洞

**初版把补漏事件直接放进了 welcome。**

```ts
// 初版（有漏洞）
const welcome = { ..., replay: result.events }
```

welcome 是**明文下发**的（手机此时还没有 salt，无法派生密钥）。
于是补漏事件的全部内容 —— 代码、路径、对话 —— 会以明文经过中继。
「中继只转发密文」当场破功，而且这条路径只在「重连且需要补漏」时触发，
正常测试很容易漏掉。

改法：welcome 只带 `replayCount`，事件本身随后用加密帧逐条发。
`relay-e2e-encrypted.test.ts` 里那条
`welcome 本身不含载荷（含 replay 事件就说明明文漏了）`
就是为这个漏洞写的，注入回旧实现会立刻红。

### 15.5 一处 off-by-one（第一帧就被判重放）

`recvCounter` 初值写成 `0`，于是对端发的第一帧（计数 0）被判成
「不新于已见 0」→ `FRAME_REPLAYED`，一条合法连接从第一帧起永远解不开。

用 `-1` 表示「还没接受过任何帧」。这个错误是探针脚本跑出来的，
不是读代码看出来的 —— 它只在「第一次通信」时暴露。

### 16.2 一条贯穿 B3 的方法

B3 六批里，**改代码的时间很少**，绝大多数花在两件事上：

1. **先确认缺陷是不是真的** —— 写探针跑一遍，而不是读代码猜。
   §12 的「重启后设备表丢失」、§15.5 的 off-by-one 都是这么发现的。
2. **做完再注入错误，看测试会不会红** —— 累计 **27 种错误实现**：
   表格里 23 种（§6 3、§9.6 3、§11.7 3、§12.6 3、§14.8 6、§15.7 5），
   正文里 4 种（§10 `checkPayload` 未接线、§11 `tier` 回 `'push'`、
   §11 base64/hex 判断去掉、§14 默认绑回环 —— 最后这条只有 netstat 脚本能抓到），
   其中 **2 次注入后测试仍然全绿**，每次都说明「我以为覆盖了，其实没有」：
   - `close` 不删连接对象（§14.10）—— `probe()` 用 `readyState` 判活，
     行为完全正确，只是集合会无限增长。功能测试抓不到「泄漏」这类缺陷
   - 生产入口不调 `startLanStack`（§14.9）—— 组件 20 项全绿，但没人调用
