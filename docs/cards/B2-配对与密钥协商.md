# B2 · 配对与密钥协商

> 轨道 B 第 2 张卡，安全关键。B1 搭好了「白名单 + 审计」的骨架，
> B2 回答一个更要紧的问题：**凭什么相信这个请求来自我自己的手机？**

## 1. 这张卡要解决什么

B1 的服务只监听回环，`127.0.0.1` 意味着「只有本机能访问」。
但手机不在本机上 —— 它要通过中继（B3）连进来。一旦通过中继，
请求的来源就不再天然可信：任何人都可能发来一个「看起来合法」的请求。

所以 B2 要做三件事：

1. **一段一次性凭证**（二维码票据），把「物理靠近」变成「逻辑授权」；
2. **一个人工比对环节**（六位码），挡住「二维码被偷拍/截屏转发」这条最现实的攻击；
3. **一把会话密钥**（ECDH），让之后所有通信对中继不可见。

蓝图 §5 的协议原文：

```
desktop: nonce = random(16)
         ticket = { deviceId, pubKey, nonce, exp: now+90s, relayHint }
         qr     = base32(ticket)   ← 只承载票据，不承载密钥
phone  : verify(qr) → 建立 WSS → 发送 { phonePubKey, nonceEcho }
desktop: 校验 nonceEcho === nonce 且未过期 → 显示六位码供人工比对
phone  : 用户比对六位码一致 → 确认
desktop: 生成 sessionKey = ECDH(pubKeys) → 写入配对设备表
         // 之后所有信道用 sessionKey 加密，票据立即作废
```

蓝图对六位码的解释很到位，照抄在这里因为它决定了实现方式：

> 为什么还要人工比对六位码：二维码可能被肩窥或截屏转发。
> 六位码只用于首次配对，比对成功后永不重复出现。
> 这比「扫码即信任」多一步，但挡掉了「有人偷拍你的二维码就能进你的电脑」这条最现实的攻击路径。

## 3. 三个关键设计决策

### 3.1 票据一次性：保留记录标记 `used`，而不是删除

最直觉的写法是配对成功后 `tickets.delete(nonce)`。这样重放会得到
`TICKET_INVALID`（「没这张票」）—— 功能上确实挡住了，但**掩盖了攻击事实**：
日志里分不出「有人拿用过的票重放」和「随手编了个 nonce」。

所以这里保留记录只标记 `used`，重放报 `TICKET_USED`。
判定顺序也是刻意的：**先判 used，再判 expired**。
一张已用的票据隔了很久再出现，应该报 `USED`（攻击特征），
报 `EXPIRED` 会让攻击者以为「只是慢了一步」。

代价是记录会堆积，所以加了 `sweepExpired()` 在成功路径上清扫，
保留窗口与 TTL 一致。**清扫不能放在判定之前** —— 那样过期票据会先被删掉，
随后报 `INVALID`，又丢掉了 `EXPIRED` 这个有用信号。这个顺序是调试中踩出来的。

同一个原则也用在「六位码试满 3 次」：不删记录，标 `used`，
让这张票的作废原因是「爆破」而不是「自然过期」，审计时能区分。

### 3.2 六位码由桌面从双方公钥派生，而不是随机数

如果六位码是随机生成再发给手机，那它只是又一个可被中间人转发的值 ——
**挡不住**蓝图担心的那个攻击。真正起作用的原因是它绑定了公钥：

- 桌面：用自己的私钥 + 手机公钥算 ECDH 共享秘密 → HMAC → 六位码；
- 手机：用自己的私钥 + 桌面公钥算共享秘密 → 同一个 HMAC → 同一个六位码；
- 中间人换了公钥 → 共享秘密不同 → 两端六位码不同 → 用户比对时一眼看出。

单测里有一项专门验证这个：`公钥被替换后两端六位码不同`。
这一项如果失败，说明六位码退化成了装饰品。

六位码只有 100 万种可能，所以必须有尝试上限。超过 3 次直接作废票据，
让爆破失去继续试的机会 —— 这比「只报错不作废」更安全。

### 3.3 配对判定放在「读参数」之前

`server.ts` 现在的四道判定顺序：

```
白名单（CHANNEL_DENIED）→ 配对（DEVICE_REVOKED）→ 读参数（400）→ 分发
```

配对放在读参数之前，有两个理由：

1. 未配对设备不该有提交 payload 的机会 —— 少一个输入面就少一类攻击；
2. 减少信息泄露：未配对时无论 payload 是什么，响应都一样，
   不给对方探测「这个通道对参数怎么反应」的机会。

白名单仍在最前：它回答的是「这个能力是否允许远程调用」，
配对回答的是「你是谁」。前者是静态策略，后者是身份，顺序不能反 ——
反了的话，未配对设备能通过响应差异枚举出白名单有哪些通道。

### 接入是真实的，不是「有个函数没人调用」

`relay-pair-gate.test.ts` 发的是**真实 HTTP 请求**，断言的是响应码：

- 未配对设备 → `403 DEVICE_REVOKED`
- 配对成功后同一设备 → `200` 且拿到真实数据

- 判定顺序：白名单外的通道先撞 `CHANNEL_DENIED`，白名单内未配对才是 `DEVICE_REVOKED`

## 6. 调试中踩到的两个坑（都会导致「假失败」）

1. **`beforeEach` 与 `makeService()` 双重初始化 clock**：
   两处都设时钟，后设的覆盖前者，出现「票据已过期但测试以为还没到」。
   删掉 `beforeEach`，统一由 `makeService()` 重置。

2. **测试重复调用同一票据**：
   `expect(...).toThrowError()` 执行一次、`try` 块又执行一次。
   而过期分支会顺手删除票据，于是第二次拿到 `TICKET_INVALID`，
   看起来像「过期没报对」。改成一次捕获即可。

这两个都不是产品代码的错，但会让人误改正确的代码 —— 所以记在这里。

## 7. 已知限制

1. **`pairing` 参数是可选的。** 不传就退化为 B1 行为（仅回环、无设备鉴权）。
   这是刻意的兼容设计（B1 的 netstat 验收依赖它），但**运行时必须传**。
   B3 接入中继时若不传，等于通道没有身份校验 —— 这条要写进 B3 的检查项。
2. **桌面长期密钥对只在进程内存里**，重启即换，所有已配对设备会失效。
   长期密钥的持久化（写入用户数据目录、用 safeStorage 保护）属 B3。
   当前实现能通过全部四条验收，但用户体验上「重启要重配」不可接受。
3. **会话密钥已用于鉴权，但尚未用于加密。** `sessionKey` 现在参与每个请求的
   HMAC 签名（见 §11），所以「知道 deviceId 就能冒充」的漏洞已经堵上。
   但 HTTP 报文本身仍是明文 —— 回环内可接受，跨设备必须靠 B3 的 WSS 加密。
4. **二维码用 base64url 而不是蓝图写的 base32。** Node 无内置 base32，
   base64url 同样可放进 URL 且无歧义，信息量一致。手机端解码时注意。
5. **未做票据签发频率限制。** 每次点「显示二维码」就签发一张，
   极端情况下会堆积（虽有 TTL 清扫）。桌面 UI 层可加节流。
6. **六位码通过什么渠道展示给用户未实现。** 桌面设置页二维码 + 六位码的 UI
   属于 C 组设置页；B2 只提供 `issueTicket()` 返回的 `code`。

## 8. 与蓝图的偏差

| 蓝图 | 实际 | 原因 |
|---|---|---|
| `qr = base32(ticket)` | `base64url(ticket)` | Node 无内置 base32；base64url 同样 URL-safe 且无歧义 |
| 设置页二维码 | 未做 UI，只提供 `issueTicket()` | 桌面设置页 UI 属 C 组；B2 只保证协议与判定 |
| 手机端 `pair/` 目录 | 未做 | 手机端扫码界面属后续 C 组；本轮是桌面侧服务 |

## 10. 交付前审查：抓到一个真实安全漏洞

按 deliverable-quality 做的第二轮审查。这轮的办法不是重读文档，而是**写探针模拟攻击**：
如果我是攻击者，我能不能只凭一个字符串就拿到用户数据？

### 漏洞：明文设备头 = 没有鉴权

初版 `server.ts` 的判定是这样的：

```ts
const deviceId = req.headers['x-morrow-device']
pairing.requirePaired(deviceId)   // 只是查表里有没有这个 id
```

探针跑出来（自己配一台设备，然后**不带任何密钥**、只填 `x-morrow-device: phone-real`）：

```
真机请求: 200 {"ok":true,"data":[{"id":"secret-session"}]}
攻击者仅凭 deviceId: 200 {"ok":true,"data":[{"id":"secret-session"}]}
>>> 漏洞确认：只要知道 deviceId 就能拿到全部数据
```

**这是最高级别的缺陷**：整张 B2 卡的意义就是「证明这个请求来自我的手机」，
而结果是任何知道一个字符串的人都能通过。`sessionKey` 算出来了却完全没参与判定 ——
ECDH 白算了，配对流程退化成了「知道一个名字就行」。

而且这条通道能「发指令、批权限」（见 B1 白名单）。这个漏洞等于把桌面交出去。

### 修复：请求签名 + 时间窗

`sessionKey` 现在参与每个请求的 HMAC：

```
signature = HMAC-SHA256(sessionKey, deviceId \n channel \n timestamp)
```

三个细节都是必要的，少一个就能绕过：

| 要素 | 少了会怎样 |
|---|---|
| sessionKey | 就是上面那个漏洞：知道 deviceId 即可冒充 |
| channel 纳入签名 | 拿「读会话列表」的签名去调「批权限」，横向越权 |
| timestamp + 60s 时窗 | 签名可被无限期重放，抓到一次就永久有效 |

对比用 `timingSafeEqual`，避免通过响应时间逐字节猜签名。

### 复验

同一个攻击探针再跑一次：

```
真机请求: 403 DEVICE_REVOKED
攻击者仅凭 deviceId: 403 DEVICE_REVOKED
>>> 设备头不足以冒充（请求被拒）
```

`relay-pair-gate.test.ts` 从 9 项增到 15 项，新增 6 项专门覆盖攻击面：

- 只知道 deviceId、没有 sessionKey → 403
- 只带设备头、不带签名 → 403
- 签名被篡改 → 403
- 拿 A 通道的签名调 B 通道 → 403（横向越权）
- 时间戳超出窗口 → 403（重放）
- 时钟窗口内（±30 秒）可用（确认没把正常漂移也挡掉）

### 这一条要记住的教训

我上一轮报告里写的是「sessionKey 已协商但**尚未用于加密**」——
说法**把风险说轻了**。真实情况是「尚未用于加密，**也没有用于鉴权**」，
而后者是安全漏洞，前者只是性能/隐私权衡。写限制时不能用「未加密」含糊带过鉴权问题。

## 11. 下一张卡

**B3 传输层**：三级回退（LAN WSS → 中继 WSS → FCM + 拉取）+ seq 补漏 +
ring buffer（2000 条）+ `snapshot_required` 降级。

B3 必须解决 B2 留下的限制：
1. **桌面长期密钥要持久化**（否则每次重启所有设备失效）；
2. **HTTP 报文加密**（签名解决了「你是谁」，没解决「内容被看见」）；
3. **`pairing` 变成运行时强制**（不传即拒绝启动，而不是静默退化为无鉴权）。

顺带一提：本轮修复后的签名机制在 B3 应当**保留**，作为 WSS 之上的应用层二次校验 ——
纵深防御，传输层被破时还有一层。
